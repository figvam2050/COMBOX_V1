# Заводська прошивка COM-Box (Felicity Solar G5RC) — повний розбір

Джерело істини: **лише** `combobox_bkp_40000.bin` (дамп 256 КБ з flash).
Жодні сторонні документи проєкту (`ANALYSIS.md`, `PORT_MAPPING.md`, `FACTORY_PIN_ANALYSIS.md`)
при складанні цього файлу **не використовувалися**. З header'ів дозволені тільки
`lib/GD32F30x/include/*.h` (нумерація IRQn, назви реєстрів) — виключно для того, щоб
перетворити числові адреси на імена периферії.

---

## 0. Методика та достовірність

| Що | Як перевірено |
|---|---|
| Адреси функцій, виклики `bl`/`b.w`/`blx` | capstone 5.0.6, Thumb-2 + M-class, прямий дизасембл байтів `.bin` |
| Літерали `ldr rX, [pc, #N]` | читання 4 байтів за `align4(pc+4)+N` |
| Імена периферійних реєстрів | числове значення літералу → звірка з `gd32f30x.h` / `gd32f30x_can.h` |
| IRQ-вектори | слово з векторної таблиці на `0x08000004+4*n` → `16 + IRQn` |
| Непрямі виклики (`blx reg`, tbb) | частково — розкладені вручну |

**Рівні впевненості** в тексті: *(доведено)* — перепідтверджено з коду в цій сесії;
*(раніше)* — отримано на попередніх етапах реверсу, не перечитувалося зараз;
*(ймовірно)* — логічний висновок, який варто перевірити.

Файли-помічники лежать поруч:
* `combobox_bkp_40000.bin` — оригінальний бінарник;
* `dumps/combobox_bkp_40000.asm` — лінійний Thumb-дамп усієї області коду (≈128 тис. рядків);
* `tools/radare.py` — рекурсивний дизасемблер, будує дерево викликів, шукає периферійні літерали,
  пише `db.json` + `periph_report.txt`;
* `tools/dump.py`, `tools/ctx.py`, `tools/disasm.py`, `tools/recon.py` — дрібні утиліти для
  дизасемблювання діапазону адрес;
* `tools/periph_report.txt` — готовий звіт про периферійні літерали.

Відтворення (усі шляхи відносні, `capstone` має бути встановлений):
```bash
cd original_firmware
python3 tools/radare.py [шлях_до.bin]   # за замовчуванням бере ../combobox_bkp_40000.bin
                                        # пише tools/db.json і tools/periph_report.txt (~1 c)
python3 tools/dump.py 0x0800715A 0x08007280   # дизасембль діапазону
                                              # (якщо адреси немає в db.json — raw fallback з .bin)
python3 tools/dump.py x 0x08007458            # хто викликає цю адресу (xrefs)
python3 tools/ctx.py 0x08007458               # 0x40 байтів до / 0x30 після адреси
```

## 1. Загальна структура бінарника

* **MCU:** GD32F305 (Cortex-M4F), base `0x08000000`, 256 КБ flash.
* **Апаратна мапа:** bootloader `0x08000000` (відомий за магічним словом `G5RC`),
  застосунок `0x08004000`, `VTOR` для застосунку = `0x08004000`,
  початковий SP з слова `0x08004000` = `0x20003278` *(раніше)*.
* **Старт:** Reset_Handler → `SystemInit` (`0x080051E4`) →
  `0x08004154` (встановити SP, scatter-load коду/даних `0x08004238`) → **`main = 0x08005924`** *(раніше)*.
* **`main` (0x08005924)** викликає послідовно *(раніше, підтверджено літералами)*:
  1. `0x8005A94` — рання ініціалізація;
  2. `0x8007894` = `0x8007110` (flash-id) + `0x8006F78` (GPIO) + `0x80061A8` (**CAN init**)
     + `0x80082FC` → `0x8008388` (**USART0 init / UART4 init**);
  3. `0x80078B0` — **SysTick**: `LOAD = HCLK/1000 − 1`, `VAL = 0`, `CTRL = 7`
     (tickint + clksource) → **тикає 1 раз на 1 мс** *(доведено в цій сесії)*;
  4. `0x80078F4(0, 0x20, 2, 3)` і `0x80078F4(1, 0x20, 2, 9)` — реєстрація двох
     «портових об'єктів» (див. §6);
  5. `0x8006E50(0,2,3)`, `(1,2,4)`, `(2,2,5)`, `(3,2,6)` — таблиця ролей 4 каналів
     (`RAM[chan] = 2`, `RAM[chan+4] = 3..6`) *(доведено: `0x8006E50` — це просто два `strb`)*;
  6. `0x80076B4` — таблиця параметрів
     `(0x0B,1,0) (0x25,5,2) (0x35,5,1) (0x14,3,0) (0x15,3,1) (0x13,3,2) (0x16,6,0)`;
  7. `0x8004F90` — ініціалізація ядра RTOS (таймери/події/черги);
  8. **4× `task_create`** (див. §2);
  9. дефолти в `0x20001088`:
     `+0x04 = 0x14`, `+0x06 = 0`, `+0x10 = 0x64`, `+0x12 = 1`,
     `+0x1C = 0x14`, `+0x1E = 0x0E`, `+0x28 = 0x64`, `+0x2A = 0x12` *(доведено)*;
  10. `0x80050B4()` — **запуск планувальника** (хвостовий перехід у `0x8004196` = перший контекст).

## 2. RTOS: задачі, події, таймери, перемикання

### 2.1 API ядра

| Адреса | Значення | Доведено |
|---|---|---|
| `0x080050E0(entry, stack_words, idx)` | **task_create**: віднімає `stack_words*4` від верху стеку, будує початковий кадр через `0x0800511C`, пише SP у TCB `base + idx*12`, виставляє біт готовності | *(доведено)* |
| `0x0800511C(sp)` | фабрика початкового кадру: `xPSR=0x01000000`, `PC=entry`, `LR=0xFFFFFFFD`, `R0=0`, `R1..R11 = 0x0n0n0n0n` | *(доведено)* |
| `0x080050B4()` | scheduler start: обчислює масив TCB, `b.w 0x8004196` (перший запуск) | *(доведено)* |
| `0x0800500C(mask)` | **event_wait_and_clear**: якщо `pending & mask ≠ 0` → очистити й повернути; інакше зняти біт готовності поточної задачі, викликати `0x8005074()` (контекстне перемикання) і повернути | *(доведено)* |
| `0x08004EC4(idx, bit)` / `0x08004F5C(idx, bit)` | **event_post**: `events[idx].pending \|= 1<<bit`; якщо `pending & enabled ≠ 0` → `ready_mask \|= 1<<idx` | *(доведено)* |
| `0x08004188` / `0x08004190` | критична секція enter / exit | *(доведено)* |
| `0x08004FE0` | ініціалізація **4 подієвих блоків** по 12 байт: `+8 = pending (u16)`, `+0xA = enabled (u16) = 0xFFFF` | *(доведено)* |
| `0x08005074()` | планувальник: `0x8004F08()` = вибір найвищої готової задачі → `0x20000092` (u16 mask), `0x20000094` (u8 № поточної), `0x20000098` (ptr на TCB) → `0x80041B0()` = **запуск PendSV** | *(доведено)* |
| `0x080051D4` | SysTick ISR: лічильник `*literal++`, потім `b.w 0x8005198` | *(доведено)* |
| `0x08005198` | сканер **4 таймерів** (крок 0xC); коли лічильник досяг порогу → `0x8004F5C(timer_idx, 0)` = **пост bit0 задачі з тим самим індексом** | *(доведено)* |

Ключова властивість: **індекс таймера = індекс задачі**, і кожен таймер шле своїй задачі `bit0`.
Тому `bit0` у кожній задачі — це її періодичний «тикач».

### 2.2 Чотири задачі

Виклики в `main` *(доведено з літералів `0x80059D8/59E0/59E4/59E8`)*:

```c
task_create(0x08008229, 0x100 /*256 слів = 1 КБ*/, 0);   // літерал 0x80059D8
task_create(0x08007081, 0x100, 1);                       // літерал 0x80059E0
task_create(0x0800715B, 0x100, 2);                       // літерал 0x80059E4
task_create(0x0800713D, 0x100, 3);                       // літерал 0x80059E8
```

| idx | Вхід | Призначення |
|---|---|---|
| **0** | `0x08008228` | **Диспетчер команд** (див. нижче) |
| **1** | `0x08007080` | «Службова/очікування» |
| **2** | `0x0800715A` | **Головна задача протоколів** |
| **3** | `0x0800713C` | Такт: 100 мс LED/RS485 DE + годування IWDG |

#### Задача 0 — `0x08008228` (диспетчер команд) *(доведено)*

```
0x8008228: 0x80082A8()              ; обнулити два байти
0x800822C: 0x800500C(1)             ; чекати bit0
0x8008232: 0x800500C(1)             ; чекати bit0
r4 = 0x200000FE                      ; байт «поточна команда / тип виробу», літерал 0x80082A4
loop:
  switch (*0x200000FE) {
    case 0: 0x8007700();  break;   // визначення типу пристрою (див. §9)
    case 1: 0x8008194();  break;
    case 2: 0x8005F0C();  break;
    case 3: 0x8006604();  break;
    case 4: 0x80064E4();  break;
    case 5: 0x8008134();  break;
    case 6: 0x8006E60();  break;   // розкодування подій → канал (0..9)
    case 7: 0x80080B4();  break;
    case 8: 0x80082BC();  break;   // чекає події, пише в 0x200000FE код 7/9/6/1
    case 9: 0x8008418();  break;
    default: *0x200000FE = 0;
  }
```

Кожна гілка — це «стан, що чекає подію»: `0x800500C(0xFFFF)` повертає маску
встановлених бітів, і за допомогою ланцюжка `lsls r1, r0, #k; bpl` код вибирає
**наступну команду** (біт `31-k` → команда) і записує її в `0x200000FE`.
Якщо жоден біт не підійшов — повертається на початок очікування.

**Повна таблиця гілок задачі 0** *(доведено в цій сесії, розбір `tools/disasm`)*:

| Команда | Гілка | Перед очікуванням | Біт → наступна команда | Призначення |
|---|---|---|---|---|
| 0 | `0x8007700` | — | див. §9 | визначення типу виробу |
| 1 | `0x8008194` | `0x8007FCC(1)` (прапорець), `0x80080A4(0)`, `0x8008094(0)` | 7→7, 9→9, 6→6, 3→4, 4→3, 2→2; 0→тикер `0x80081F8(0x96=150)` | стан «чекаємо BMS» |
| 2 | `0x8005F0C` | `0x8007FCC(1)` | 7→7, 9→9, 6→6, 4→3, 5→5, 3→4 | |
| 3 | `0x8006604` | `0x8007FCC(1)`, `0x8007C1C(0)`, `0x8008094(1)` | 7→7, 9→9, 6→6, 2→2; 0→тикер `0x2EE=750` | |
| 4 | `0x80064E4` | `0x8007FCC(1)`, `0x8007BE4(0)`, `0x8008094(1)` | 7→7, 9→9, 6→6, 5→5, 2→2; 0→тикер `0x2EE=750` | |
| 5 | `0x8008134` | `0x8008094(1)`; попередньо 25 тактів `wait(1)` + цикл `0x8008E1C()` | 7→7, 9→9, 6→6, 3→4 | |
| 6 | `0x8006E60` | `0x800903C() ≥ 300` → `0x8007FCC(1)` + `0x8004EC4(2,6)`; `0x8008094/8058/8068(0)`; `*(u8*)0x200000B4++` | 7→7, 9→9, 3→4, 10→0, 1→1 | |
| 7 | `0x80080B4` | 10 тактів; `0x8008DDC()`; `0x8007BC8(0)`; якщо `0x800903C() ≥ 30` → `0x8007FCC(1)`, `0x8004EC4(2,5)`, `0x8004EC4(2,6)`; далі 25 тактів і цикл `0x8008E1C()` | — | |
| 8 | `0x80082BC` | `0x8007FCC(0)`, `0x8008094(0)` | 7→7, 9→9, 6→6, 1→1 | |
| 9 | `0x8008418` | 25 тактів `wait(1)` | — | **ввід у режим прошивання** (див. §13.8) |

`0x8008094(bit)` / `0x80080A4(bit)` / `0x8008058(bit)` / `0x8008068(bit)` —
сеттери біт-полів (`bfi`) у словах `0x2000000A` / `0x200000BC` / `0x20000014`;
`0x8007C1C(bit)` = `bfi` у `0x200000BC`, `0x8007BE4(bit)` = `bfi` **біт 5** у
`0x200000BC`. Парні «увімкни/вимкни» `0x8007FBC(x)` / `0x8007FCC(x)` — це
`bfi` **біт 1** і **біт 0** одного 16-бітного слова `*(u16*)0x2000000A`
(біти 6–7, 8–9, 10–11 того самого слова ставлять `0x8007F08` / `0x8007FB0` /
`0x8007F40`) — тобто **свій, програмний прапорець «стану»**, не RTOS-подія.

**`0x800500C(mask)` — очікування подій саме поточної задачі** *(доведено в цій
сесії з тіла функції)*:
```c
tcb = *(0x2000009C);            // TCB поточної задачі
tcb->wait = mask;               // +0x0A
got = tcb->flags & mask;        // +0x08
if (got) { tcb->flags &= ~mask; return got; }
ready_mask(0x20000090) &= ~(1 << current_idx(0x20000094));
0x80041B0();                    // PendSV -> переключення
return tcb->flags & mask;
```
TCB-таблиця: база **`0x20001088`**, крок **0xC** (`+0` = SP, `+8` = u16 встановлені
біти, `+0xA` = u16 маска очікування).
`0x8004EC4(idx, bit)` = `tcb[idx].flags |= 1<<bit`; якщо `flags & wait != 0` —
`*(u16*)0x20000090 |= 1<<idx` (біт готовності).
`0x8004F5C(idx, bit)` — те саме без перевірки готовності.
Суміжні слова: `0x20000090` = бітова маска готових задач, `0x20000092` = скретч,
`0x20000094` = індекс поточної задачі, `0x20000098` = вказівник на її TCB.

**Отже цикли `0x800500C(1)` × 10 або × 25 у гілках — це рахунок системних тактів**
(SysTick шле `(task_idx, bit0)`, §2.4), тобто затримка 10 / 25 тиків;
`0x800500C(0xFFFF)` = «чекаю будь-яку подію».

`0x8008194`-подібний «тикер» `0x80081F8(N)`: рахує такти в `*(u16*)(0x200000B4+2)`,
і коли лічильник досягає `N` — скидає його і викликає `0x80080A4(1)`.
Ідентичний `0x800665C(N)` (`*(u16*)(0x200000B4+4)`) і `0x8006544(N)`
(`*(u16*)(0x200000B4+6)`), тобто **три незалежні таймери-затримки**.

**Дрібні гетери, які кличуть гілки** *(усі розшифровані — однобітові читання
з фіксованих RAM-слів)*:

| Функція | Що повертає |
|---|---|
| `0x8008E1C()` | біт **1** `*(u8*)0x2000000A` |
| `0x8008E2C()` / `0x8008E3C()` | біт **0** / біт **2** того самого `0x2000000A` |
| `0x8008E4C()` | біт **0** `0x200000B2` («ініціалізацію завершено») |
| `0x8008E5C()` | `*(u8*)0x20000022` (сире DIP) |
| `0x8008E74()` | `*(u8*)(0x20000022+1)` |
| `0x8008E68()` | `*(u8*)0x20000026` (профіль/тип) |
| `0x8008E80()` | біт **4** `*(u8*)0x200000BC` (викликає тільки тікер `0x80081F8`) |
| `0x8008DFC()` / `0x8008E0C()` | біт **5** / біт **6** того самого `0x200000BC` |
| `0x8008DDC()` | біт **8** `*(u16*)0x2000005E` (дзеркало `0x8007BC8(x)`) |
| `0x8008DEC()` | біт **0** `0x2000005E` |
| `0x800903C()` | `*(u32*)(0x2000004C + 0x38)` = **`0x20000084`** — лічильник, який
  порівнюють із **30** (гілка 7) та **300** (гілка 6) |
| `0x8008E90()` | читання **DIP PB15..PB12** (маски `0x8000/0x4000/0x2000/0x1000`,
  активний низький → 8/4/2/1), `cmp r4, #0x10` |

Підтвердження: `0x8007BC8(x)` = `bfi` **біт 8** у `0x2000005E`, а `0x8008DDC()`
читає рівно цей біт; `0x8007C1C/0x8007BE4` працюють із `0x200000BC`
(біти 5/6 дзеркалуються `0x8008DFC`/`0x8008E0C`).

**Ключова подія `bit9`:** магічний кадр `G5RC\r` на RS485 (`0x800748C`) або звірка
адреси (`0x8007A10`) шле `0x8004EC4(0, 9)` → задача 0 отримує `bit9` → гілка
`case 9 → 0x8008418` → **стирання магії застосунку і перезехід у bootloader**
(§13.8) *(доведено в цій сесії)*.

`0x80082A8()` на старті задачі: `*(u8*)0x200000FE = 0; *(u8*)0x200000B4 = 0`.

Ініціалізація периферії, яку кличе задача/стартовий блок:
* `0x80082FC()` — **USART0**, піни **PA9 (AF PP) / PA10 (input float)**, база
  `0x40013800`, швидкість `0x2580 = 9600`, `CTL = 0x305`;
* `0x8008388()` — **UART4**, піни **PC12 (TX) / PD2 (RX)**, база `0x40005000`,
  ті самі параметри.
  Виклики: `0x80078A2 → 0x80082FC`, `0x80078AA → 0x8008388` (обидва з `0x8007894`).
  *(Доведено; узгоджується з §4.1/§4.2.)*

#### Задача 1 — `0x08007080` *(доведено)*

```
while (0x8008E4C() == 0) 0x800500C(1);   // чекає біт0, поки не встане прапорець 0x200000B2.0
*0x200000A8 = 0;
for (;;) 0x800500C(0xFFFF);              // далі лише «проковтує» події
```

#### Задача 2 — `0x0800715A` (головна) *(доведено, повний цикл)*

```
bl 0x8007280                 ; разовий старт: 0x80069C0 + перевірки 4 слотів
loop@0x8007162:
  flags = 0x800500C(0xFFFF)
  bit1 → 0x8007458(0)                                   ; кадр каналу 0
  bit9 → 0x800799C(1); 0x8008E68()∉{1,2,3} → 0x8007458(1)
  bit4 → 0x8007FBC(1); 0x8006CDC(); 0x8007FBC(0); 0x8005F58()   ; слот 0x100
  bit3 → 0x8007FBC(1); 0x80066B0(); 0x8007FBC(0); 0x8007BD8(0x8009A3C()+1)
  bit2 → 0x8006B0C() (+0x8007FBC/0x8007BD8)             ; слот 0x300
  bit5 → 0x8006824() (+0x8007FBC/0x8007BD8)             ; слот 0x400
  bit0 → 0x8007A64(0,2); 0x8007A64(1,2); 0x8006590(0,750);
         0x80070A8(0,50); 0x8006DE8/67BC/6C14/6930(100);
         0x8006C80(9000); 0x8007754(0,50,5)             ; CAN-планувальник + Modbus-опитування
```

**`bit0` — це щось на кшталт «100 мс»** (періодично шле всі планувальники) *(ймовірно)*.

#### Задача 3 — `0x0800713C` *(доведено)*

```
for (;;) {
  flags = 0x800500C(0xFFFF);
  if (flags & 1) { 0x800737C();   // 100-мс такт: LED + RS485 DE/RE
                   0x80057F8(); } // годування IWDG
}
```

### 2.3 Такт `0x0800737C` — світлодіоди та напрямок RS485 *(доведено)*

```
r4 = 0x40011000 (GPIOC)     r5 = 0x40010C00 (GPIOB)     ; літерали 0x8007450/0x8007454
*0x200000AC = (*0x200000AC + 1) % 10
*0x200000AA = (*0x200000AA + 1) % 20
*0x200000AE = (*0x200000AE + 1) % 2
*0x200000B0 = (*0x200000B0 + 1) % 4
switch (*0x200000FE) {           // тип виробу
  case 6: t = cnt10; th = 5;  break;
  case 1..4: t = cnt20; th = 10; break;
  case 0: t = cnt2;  th = 1;  break;
  default: t = cnt4;  th = 2;  break;
}
if (t >= th) { gpio_bit_set(GPIOC, 0x2000);   gpio_bit_reset(GPIOB, 1); }
else         { gpio_bit_reset(GPIOC, 0x2000); gpio_bit_set  (GPIOB, 1); }
if (*0x20000014 != 0) gpio_bit_set  (GPIOB, 2);   // інакше reset
if (*0x20000088[0] != 0) gpio_bit_set (GPIOC, 0x20); else gpio_bit_reset(GPIOC, 0x20);
0x8008488();   // -> byte[0x20000014]
```

Допоміжні «генери», які тут використовуються:

* `0x08005818(gpio, mask)` = `*(u32*)(gpio + 0x14) = mask` → **`GPIO_BC` = скидання біта (LOW)** *(доведено)*;
* `0x0800581C(gpio, mask)` = `*(u32*)(gpio + 0x10) = mask` → **`GPIO_BOP` = встановлення (HIGH)** *(доведено)*;
* `0x08005820(gpio, mode, cfg, pin_mask)` — налаштування піна:
  виклики `…(GPIOx, 0x18, 2, <mask>)` = AF push-pull 50 МГц (TX),
  `…(GPIOx, 4, 2, <mask>)` = вхід/флоат (RX) *(доведено з `0x80082FC`/`0x8008388`)*.

**Висновок щодо пінів, які точно встановлюються в такті:**

| Пін | Роль | Доведення |
|---|---|---|
| **PC13** | LED «A» (мігрує залежно від типу виробу) | `gpio_bit_*(GPIOC, 0x2000)` |
| **PB0** | LED «B», **дзеркально протилежний до PC13** | `gpio_bit_*(GPIOB, 1)` |
| **PB1** | LED стану: **HIGH, поки очікується відповідь від BMS** (`*0x20000014 ≠ 0`) | `gpio_bit_*(GPIOB, 2)` |
| **PC5** | **RS485 DE/RE**: HIGH → передавач увімкнено | `gpio_bit_*(GPIOC, 0x20)` + `*0x20000088[0]` |

Слово `*0x20000088[0]` формується в `0x08007104` / записується в `0x08007100`
(байт `0x20000088`), тобто це «зараз ми передаємо» *(доведено частково)*.

Шаблон блимання PC13/PB0 кодує `0x200000FE` (тип виробу), тобто **дві LED показують режим пристрою**.

### 2.4 Джерела подій — хто шле біти задачам *(доведено в цій сесії)*

Усі місця виклику `0x8004EC4(idx, bit)` (event_post), знайдені `tools/xref.py`:

| Сайт | Виклик | Хто шле |
|---|---|---|
| `0x80051BE` | `0x8004F5C(idx, 0)` | **SysTick ISR** (`0x80051D4` → `0x8005198`): для кожного з 4 таймерів (крок 0xC) шле `(timer_idx, bit0)` — **індекс таймера = індекс задачі**, тому `bit0` = періодичний тикач |
| `0x800748C` | `(0, 9)` | роутер `0x8007458`: магічний кадр **`G5RC` + `buf[6]==0x0D`** |
| `0x8007A10` | `(0, 9)` | звірка адреси `buf[5] == 0x30 + …` |
| `0x8009150` | `(0, 7)` | після `0x8007BC8(1)` (сервісна гілка) |
| `0x8006E76` | `(2, 6)` | `0x8006E60`-контекст, після `0x8007FCC(1)` |
| `0x80080E2` / `0x80080EA` | `(2, 5)` | якщо `адреса ≥ 0x1E` (`cmp r0,#0x1e; blo`) → `0x8007FCC(1)` |
| `0x8007AC8` | **`(ch[+0x200], ch[+0x201])`** | **універсальний пост із структури каналу**: `ldrb r1,[r4,#0x201]` (біт), `ldrb r0,[r4,#0x200]` (індекс задачі). Ці поля пише `0x80078F4(ch, …, mode, id)` — `+0x200 = mode`, `+0x201 = id` |
| `0x8006812` | `(byte[0x2000000D], byte[0x20000011])` | планувальник `0x80067BC` (період 100) |
| `0x800698C` | `(byte[0x2000000F], byte[0x20000013])` | планувальник `0x8006930` (період 100) |
| `0x8006C6C` | `(byte[0x2000000E], byte[0x20000012])` | планувальник `0x8006C14` (період 100) |
| `0x8006E3E` | `(byte[0x2000000C], byte[0x20000010])` | планувальник `0x8006DE8` (період 100) |

**Чотири пари конфігурації «планувальник → задача/біт»** живуть парами
`{ task[4] @0x2000000C..0x0F } × { bit[4] @0x20000010..0x13 }`
і саме вони генерують **`bit1 … bit4` головної задачі** (якщо `task=2`).

`0x8006E50(a, b, c)` — запис у таблицю налаштувань:
`table[a] = b; table[a+4] = c`, виклики `(0,2,3), (1,2,4), (2,2,5), (3,2,6)`.

Висновок: **`bit1` (кадр каналу 0), `bit2/3/4/5` (слоти), `bit9` (сервіс) — події від
планувальників/каналів; `bit0` — системний тик; `bit5/6` — команди.**

## 4. Порти зв'язку

### 4.1 USART0 — головний RS485 (майстер BMS) *(доведено)*

Ініціалізація `0x080082FC`:
```
0x8005EB8(0x60E)            ; RCU: увімкнути годування USART0
0x8005EB8(0x602); 0x8005EB8(0x602)
gpio_init(GPIOA, mode=0x18, cfg=2, pin=0x200)   ; PA9  = TX, AF push-pull
gpio_init(GPIOA, mode=4,    cfg=2, pin=0x400)   ; PA10 = RX, вхід
```
* `0x8005EB8(x)` = **RCU peripheral clock enable** *(доведено за використанням)*.
* База периферії: `0x40013800` (USART0), літерали `0x80052CC, 0x8007AEC, 0x8007B0C, 0x8007B28, 0x8008384, 0x8008F1C, …`.
* Швидкість **9600 8N1** *(раніше)*.
* **Напрямок передавача: PC5** (§2.3) через `*0x20000088[0]`.

### 4.2 UART4 — другий UART *(доведено)*

Ініціалізація `0x08008388`:
```
0x8005EB8(0x10)                           ; годування GPIOC/GPIOD
0x8005EB8(0x20)                           ; годування UART4
gpio_init(GPIOC, mode=0x18, cfg=2, pin=0x1000)   ; PC12 = TX
gpio_init(GPIOD, mode=4,    cfg=2, pin=4)        ; PD2  = RX
```
* База `0x40005000`; літерали `0x800527C, 0x8007AE8, 0x8007B08, 0x8007B24, 0x8008414, 0x8008F20, …`.

### 4.3 UART3 *(раніше)*

База `0x40004C00`, літерали `0x8009EC8, 0x8009F30`. Піни окремо не відновлені.

### 4.4 Єдиний драйвер UART з індексом каналу *(раніше)*

`0x8007AD0` / `0x8007AF0` / `0x8007B16` — дескриптори; `0x8007B70(ch, buf, len)` = **TX**.
`0x80078F4(ch, 0x20, mode, id)` виділяє об'єкт каналу розміром **0x206 (518) байт**
через `0x8004222(ptr, 0x206)` і пише `*(ptr+0x200)=mode`, `*(ptr+0x201)=id`
(для ch0 → id=3, для ch1 → id=9) *(доведено)*.

### 4.5 Розкладка буферів каналу *(доведено)*

База `0x8005BF0 → 0x200020F0`; крок на канал = **0x206**.

| Функція | Обчислення | Роль |
|---|---|---|
| `0x08005BC4(ch)` | `0x200020F0 + ch*0x206 + 2` | **RX-буфер кадру** |
| `0x08005BDC(ch)` | `0x200020F0 + ch*0x206 + 0x101` | **TX-буфер кадру** (куди слейв складає відповідь) |
| `0x08005BF4(ch)` | байт `+0x203` | статус |
| `0x08005C0C(ch)` | u16 `+0x204` | статус |

### 4.6 DIP-перемикачі → Modbus-адреса *(доведено)*

```
0x08008E90(): 4 ітерації, gpio_input_bit_get(GPIOB, 0x8000 / 0x4000 / 0x2000 / 0x1000)
              -> 4-бітове значення (bit3=PB15, bit2=PB14, bit1=PB13, bit0=PB12), активний рівень — низький
0x08007360(): v = 0x8008E90();
              *0x20000022 = v;                 // «сирий» DIP
              *0x20000023 = (v == 0) ? 0x10 : v;   // Modbus-адреса коробки (0 означає 16)
              *(u16*)0x20000024 = 0;
```
Читачі:
* `0x08008E5C()` → `byte[0x20000022]` — сире значення;
* `0x08008E74()` → `byte[0x20000023]` — **адреса коробки на шині**;
* `0x08008E68()` → `byte[0x20000026]` — тип/профіль пристрою (використовується в `0x800715A`).

Інші прапорці на байті `0x200000BC` *(доведено)*: `0x08008E2C()` = bit0, `0x08008E3C()` = bit2,
`0x08008E80()` = bit4. Прапорець `0x08008E4C()` = біт0 слова `0x200000B2`.

### 4.7 Службові константи RS485-адрес *(доведено)*

* `0x08009AA4()` → `*(u16*)(0x20000494 + 6)` — **адреса пристрою-сусіда** (див. §7);
* `0x08009AC8()` → `*(u16*)(0x20000494 + 4)`;
* `0x08009AB0(idx)` → `*(u16*)(0x20000514 + idx*2)` для `idx < 0x18`, інакше `0xFFFF`
  (таблиця з 24 u16).

## 5. Канал-роутер прийнятих кадрів — `0x08007458(ch)` *(повністю доведено)*

```
r5 = ch
r4 = 0x8005BC4()            // RX-буфер каналу
r6 = 0x8005BDC()            // TX-буфер каналу
// 1) магічне слово
if (buf[0]=='G' && buf[1]=='5' && buf[2]=='R' && buf[3]=='C' && buf[6]==0x0D)
        0x8004EC4(0, 9);    // -> задача 0, bit9 (службовий режим)

// 2) фільтр адреси приймача
if (buf[0] != 0x8008E74()       // адреса коробки з DIP
 && buf[0] != 0x8009AA4()       // адреса з 0x20000494+6
 && buf[0] != 0x1E              // BMS
 && buf[0] != 0x1F)
        return;                 // кадр не для нас

// 3) маршрутизація за роллю каналу
if (ch == 0) {
        // МАЙСТЕР: розбираємо ВІДПОВІДЬ
        0x800783C(buf, 0, cb = 0x0800920F);      // літерал 0x8007510 = 0x800920F
} else {
        // SLAVE: розбираємо ЗАПИТ
        switch (buf[1]) {
          case 0x03: 0x8007514(buf, tx, ch, 8);            break;  // FC3  read
          case 0x06: 0x80075E0(buf, tx, ch, 8);            break;  // FC6  write single
          case 0x10: q = (buf[4]<<8 | buf[5]);             // FC10 write multi
                     len = 2*q + 9;
                     0x80075E0(buf, tx, ch, (len <= 0xFF) ? len : 0xFF);
                     break;
          default: return;
        }
}
```

**Ролі каналів:**

| Канал | Роль | Чому |
|---|---|---|
| **0** | **Modbus-МАЙСТЕР** | `0x800783C` читає `buf[2]` як *bytecount* і `buf[3..]` як *data* — це формат **відповіді**; опитування відправляє `0x80070A8(0, 50)` |
| **1..3** | **Modbus-SLAVE** | `0x8007514`/`0x80075E0` читають `buf[2..3]` як *start address*, `buf[4..5]` як *quantity*, перевіряють довжину `2*q+9` — це формат **запиту**, і повертаються хвостовим викликом у функції побудови відповіді |

## 6. Modbus-МАЙСТЕР (канал 0) — опитування BMS

### 6.1 Періодичний опитувач — `0x080070A8(ch, period)` *(повністю доведено)*

```
r5 = 0x20000014                       // блок стану
counter = ++(*(u16*)(0x20000018))
if (counter <= period) return;        // ще не час
counter = 0;
r4 = 0x2000001A                       // буфер запиту
buf[0]=0x1E; buf[1]=0x03; buf[2]=0x01; buf[3]=0x00; buf[4]=0x00; buf[5]=0x20
crc = 0x8009BDA(buf, 6)               // Modbus CRC16
buf[6] = crc >> 8;  buf[7] = crc & 0xFF
if (0x80078E4(ch) == 1) return;       // TX ще зайнятий
0x8007B70(ch, buf, 8)                 // відправити
*0x20000014 = 1                       // «чекаємо відповіді» -> LED PB1
```

**Кадр: `1E 03 01 00 00 20 | CRC`** =
«прочитати **32 регістри, що починаються з 0x0100**, з пристрою **0x1E**».

Викликається з головної задачі як `0x80070A8(0, 50)` — тобто раз на 50 тиків.

### 6.2 Прийом відповіді — `0x0800783C(buf, 0, cb)` *(доведено)*

```
r4 = buf + 3            // перше слово даних
r7 = buf[2]             // bytecount (для 32 регістрів = 0x40)
r6 = 0x100              // перший внутрішній регістр
for (i = 0; i < bytecount; i++) {
        val = (buf[3+2i] << 8) | buf[4+2i]        // Big-Endian, як у Modbus
        if (cb(0x100 + i, val, param)) break;     // 0x0800920E — tbb-диспетчер
}
*0x20000014 = 0;                    // відповідь отримано -> LED PB1 гасне
0x8007BF4(ch, 1);                   // підтвердження
```

Після цього значення регістрів **0x100..0x11F** опиняються в диспетчері `0x0800920E`
(tbb-таблиця вказівників), кожне з яких пише у свій слот пам'яті,
базований на `RAM[0x20001028]`, офсети `+0x00 … +0x3E` (крок 2) *(раніше)*.

### 6.3 CRC16 — `0x08009BDA(buf, len)` *(раніше)*

Modbus: побітове реверсування байта (`0x8007336`), poly `0x8005`,
побітове реверсування 16 біт (`0x800730C`), byte-swap.
Повернене значення уже «перевернуте», тому в `0x80070A8`
`crc>>8` пишеться в `buf[6]` (low), `crc&0xFF` у `buf[7]` (high) — правильно для Modbus.

### 6.4 Інші розпарсовувачі *(доведено в цій сесії)*

**`0x08007514(buf, tx, ch, len)` — FC3-ЗАПИТ (роль slave)** *(повністю доведено)*:
```
crc_rx = (buf[len-2] << 8) | buf[len-1]     // lo першим, hi другим — стандарт Modbus
if (0x8009BDA(buf, len-2) != crc_rx) -> error 0x11
       // 0x8009BDA повертає значення з byte-swap, тому порівняння коректне
start = (buf[2]<<8) | buf[3]
qty   = (buf[4]<<8) | buf[5]
if (qty > 0x7B) -> error 0x03
len = 2*qty + 9      (значення len рахує викликавча функція; якщо >0xFF -> 0xFF)

// добір ОДИН З ЧОТИРЬОХ гетерів (вказівник, а не «база RAM»):
//   start ∈ [0x2000, 0x20C0)  && start+qty ≤ 0x20C0 -> cb = 0x0800947F
//   start ∈ [0xF800, 0xF900)  && start+qty ≤ 0xF900 -> cb = 0x08009BD1
//   start ∈ [0x4300, 0x4340)  && start+qty ≤ 0x4340 -> cb = 0x08009A0D
//   start ∈ [0xFC00, 0xFD00)  && start+qty ≤ 0xFD00 -> cb = 0x08009371
//   інакше -> error 0x12
tail -> 0x800605A(buf, tx, ch, cb)
```

**`0x080075E0(buf, tx, ch, len)` — FC6/FC10-ЗАПИТ** *(повністю доведено)*:
```
CRC, start = (buf[2]<<8)|buf[3]
qty = (buf[1] == 6) ? 1 : (buf[4]<<8)|buf[5]
if (qty > 0x7D) -> error 0x03
// діапазони (усі три піддіапазони 0x2000-вказують на ТОЙ САМИЙ колбек):
//   [0x2000,0x2040) [0x2040,0x2080) [0x2080,0x20C0) -> cb = 0x080094AB
//   [0x3300,0x3400)                                     -> cb = 0x080090A9
//   [0xFC00,0xFD00)                                     -> cb = 0x08009453
//   інакше -> error 0x12
tail -> 0x80060EC(buf, tx, ch, cb)
```

Помилки: `0x11` = CRC, `0x03` = кількість, `0x12` = діапазон адрес.
Шляхи помилок ідуть у `0x8006020`.

---

### 6.5 Відповіді слейва — `0x8006020` / `0x800605A` / `0x80060EC` *(повністю доведено)*

**`0x08006020(req, tx, ch, code)` — виняток Modbus:**
```
tx[0] = req[0]                 // адреса
tx[1] = req[1] + 0x80          // функція | 0x80
tx[2] = code                   // 0x11 / 0x03 / 0x12
crc = 0x8009BDA(tx, 3); tx[3] = crc>>8; tx[4] = crc & 0xFF
if (0x80078E4(ch) != 1) 0x8007B70(ch, tx, 5)      // якщо TX вільний
```

**`0x0800605A(req, tx, ch, getter_cb)` — відповідь на FC3:**
```
start = (req[2]<<8) | req[3];  qty = (req[4]<<8) | req[5]
tx[0] = req[0]; tx[1] = req[1]; tx[2] = qty*2        // bytecount
for (i = 0; i < qty; i++) {
        v = getter_cb(start + i, param);             // blx r3/r4
        tx[3 + 2i] = v >> 8;  tx[4 + 2i] = v & 0xFF  // Big-Endian
}
crc = 0x8009BDA(tx, 2*qty+3); tx[..] = crc>>8, crc&0xFF
if (0x80078E4(ch) != 1) {
        0x8007B70(ch, tx, len);  0x8007BF4(ch, 1);
}
tail -> 0x8007830
```

**`0x080060EC(req, tx, ch, setter_cb)` — відповідь на FC6/FC10:**
```
start = (req[2]<<8) | req[3]
qty   = (req[1]==6) ? 1 : (req[4]<<8)|req[5];   вказівник даних = &req[4] (FC6) чи &req[7] (FC10)
for (i = 0; i < qty; i++) {
        val = (data[2i]<<8) | data[2i+1];
        setter_cb(start, val, param);              // blx r2
        if (++start == 0x0000) -> виняток 0x8006020 і вихід   // переповнення адреси
}
tx[0..5] = req[0..5]                                // ехо запиту
crc = 0x8009BDA(tx, 6); tx[6] = crc>>8; tx[7] = crc & 0xFF
if (0x80078E4(ch) != 1) { 0x8007B70(ch, tx, 8);  0x8007BF4(ch, 1); }
tail -> 0x8007830
```

**`0x08007830`** — `u16[0x20000054] -> u16[0x20000052]` (байт-прапорець «відповідь сформовано»).

**Таблиця гетерів FC3 (що саме віддає слейв):**

| Діапазон | Гетер | Джерело |
|---|---|---|
| `0x2000 … 0x203F` | `0x08009B10(idx)` | `*(u16*)(0x20000414 + idx*2)` — **слоти 0x100…0x13F** |
| `0x2040 … 0x207F` | `0x08009A74(idx)` | `*(u16*)(0x20000494 + idx*2)` — **слоти 0x1100…0x113F** |
| `0x2080 … 0x20BF` | `0x08009AB0(idx)` | `*(u16*)(0x20000514 + idx*2)` — **слоти 0x300…0x317** |
| `0xF800 … 0xF80F` | `0x08009A24(idx)` | `*(u16*)(0x20001008 + idx*2)` |
| `0xF810 … 0xF8FF` | — | повертає `0xFFFF` |
| `0x4300 … 0x4327` | `0x08009A8C(idx)` | `*(u16*)(0x20000544 + idx*2)` — **слоти 0x400…0x427** |
| `0xFC00 … 0xFC1F` | `0x08009370` (tbb) | `0x8009054()` + {0,2,4,6,8,0xA,0xC,0xE} → `0x8009344`: якщо `0x8008E3C()==0` і `адреса ∈ [0x08000000, 0x08040000]` → **`*(u16*)адреса` з byte-swap**, інакше `0xFFFF` (тобто **читання власного flash як регістрів**) |

| Діапазон | Сеттер | Що робить |
|---|---|---|

| `0xFC00 … 0xFC07` | `0x08009452(reg, val)` | tbb на 8 випадків; випадки 0–2 → `0x8008078(val)`, випадок 4 → `0x8008084(val)` |

### 6.6 Реєстри 0x100…0x11F — приватний регфайл `0x20001028` *(доведено)*

`0x20001028` читається/пишеться **виключно** 64 тонкими функціями-обгортками:

* **гетери** `0x8009B34 … 0x8009BCC` (13 шт., крок 12) — `return *(u16*)(0x20001028 + off)`;
* **сеттери** `0x8009C50 … 0x8009DC4` (32 шт., крок 12) — `*(u16*)(0x20001028 + off) = val`.

Відповідність гетерів (використовуються у CAN-кадрах, §8.4):

| Функція | офсет | регістр |
|---|---|---|
| `0x8009B4C` | +0x00 | 0x100 |
| `0x8009B64` | +0x02 | 0x101 |
| `0x8009B40` | +0x04 | 0x102 |
| `0x8009B58` | +0x06 | 0x103 |
| `0x8009BA0` | +0x0A | 0x105 |
| `0x8009B70` | +0x0E | 0x107 |
| `0x8009B34` | +0x12 | 0x109 |
| `0x8009BAC` | +0x18 | 0x10C |
| `0x8009BC4` | +0x1A | 0x10D |
| `0x8009BB8` | +0x20 | 0x110 |
| `0x8009B94` | +0x28 | 0x114 |
| `0x8009B7C` | +0x3A | 0x11D |
| `0x8009B88` | +0x3E | 0x11F |

**Єдиний записувач у цей регфайл** — `0x0800920E` (tbb-диспетчер, покажчик `0x0800920F`
лежить у літеральному пулі `0x8007510` і передається в `0x800783C` як `cb`):

Тобто **`0x20001028` наповнюється виключно відповіддю BMS** (Modbus-майстер, §6.2).

## 7. Другий протокол / слоти «пристроїв»

### 7.1 Чотири групи параметрів — функції збереження у flash *(доведено)*

Із головної задачі та з `0x8007280` *(підтверджено в цій сесії — повний розбір коду)*:

| Функція | Діапазон handle | Дзеркальні handle | Банк set1 | Банк set2 (=set1+0x180) | Н |
|---|---|---|---|---|---|
| `0x08006CDC` | `0x100 … 0x13F` | `0x1100 … 0x113F` | `0x20000414` | `0x20000594` | 0x40 |
| `0x080066B0` | `0x200 … 0x23F` | `0x1200 … 0x123F` | `0x20000494` | `0x20000614` | 0x40 |
| `0x08006B0C` | `0x300 … 0x317` | `0x1300 … 0x1317` | `0x20000514` | `0x20000694` | 0x18 |
| `0x08006824` | `0x400 … 0x427` | `0x1400 … 0x1427` | `0x20000544` | `0x200006C4` | 0x28 |

**Кожна з цих функцій — «зберегти параметри групи у flash», і це єдині записи
в flash-сховища (§7.5).** Алгоритм `0x8006CDC()` (інші — тотожні):

```
1) memcpy(set1, set1+0x180 = set2, (N-1) * 2)     // 0x8006CE0..0x8006CF8
2) sum = 0; for (i=0; i<N-1; i++) sum += set2[i];  // 0x8006CFA..0x8006D0E
   set2[N-1] = sum;  set1[N-1] = sum;              // ОСТАННІЙ СЛОТ ГРУПИ = КОНТРОЛЬНА СУМА
   // 0x13F = 0x4051, 0x23F = 0xB16C, 0x317 = 0x400, 0x427 = 0x28  (див. §7.5)
3) for (h = 0x100; h < 0x140; h++) {               // 3 спроби (r7 = 3)
       if (0x8008A04(h, 1, &tmp))        → потрібно писати   // у flash НЕМАЄ
       else if (set2[h-0x100] != tmp)    → потрібно писати   // значення змінилось
       else continue;                                // збіг — нічого не робимо
       if (0x8008D40(h, 1, &set2[h-0x100])) break;  // писати RAM -> flash
   }
4) for (h2 = 0x1100; h2 < 0x1140; h2++) { ... те саме для set2 ... }  // дзеркальні ключі
5) `0x80084AC(h, set2[0])` — перевірка контрольної суми, ретрай до 3 разів на кожну
   з двох груп; `r6` = лічильник **успішно** пройдених перевірок
6) `r6 == 0` → `0x8007BAC(0x800)` (жодна група не пройшла), інакше → `0x8006574(0x800)`
```

**`0x80084AC(handle, qty)` — повністю доведено в цій сесії:**
```c
sum = 0;
for (i = 0; i < qty-1; i++) { 0x8008A04(handle+i, 1, &t); sum += t; }   // 0x80084BC
0x8008A04(handle + qty-1, 1, &stored);                                  // 0x80084DA
return (stored == sum) ? 1 : 0;                                         // 1 = ОК
```
`qty = set2[0]` — **перший слово групи = кількість записів** (0x100=64, 0x200=64,
0x300=0x18=24, 0x400=0x28=40 — точно збігається з розмірами груп у §7.4).
Отже сума рахується по `qty-1` записах, а останній слот групи — збережена сума.

**`0x8006574(mask)` = `*(u16*)(0x2000004C+0xE) &= ~mask`** (зняти прапорець),
**`0x8007BAC(mask)` = `*(u16*)(0x2000004C+0xE) |= mask`** (поставити прапорець).
З викликів: `0x8006574` ← `{0x80067A0, 0x8006914, 0x8006BFA, 0x8006DCC}`,
`0x8007BAC` ← `{0x80067AC, 0x8006920, 0x8006C06, 0x8006DD8}` — по одній парі на
кожну з чотирьох функцій збереження.

**Ключовий висновок:** `0x8008A04(reg, 1, out)` = **ЧИТАТИ** параметр із flash
(`0x800467C`/`0x8004818`/`0x80049B4`), а `0x8008D40(reg, 1, ptr)` = **ПИСАТИ**
параметр у flash (`0x80046C4`/`0x8004860`/`0x80049FC`). Обидві функції роблять
той самий switch за діапазонами регістра і викликаються **тільки з чотирьох
функцій вище та з парсерів кадрів (§7.2)**.

Виклики в головній задачі (біти 2/3/4/5) — це саме **збереження налаштувань**:
```
bit4 -> 0x8007FBC(1); 0x8006CDC(); 0x8007FBC(0); 0x8005F58()   // група 0x100
bit3 -> 0x8007FBC(1); 0x80066B0(); 0x8007FBC(0); 0x8007BD8(...)  // група 0x200
bit2 -> 0x8006B0C() (+0x8007FBC/0x8007BD8)                       // група 0x300
bit5 -> 0x8006824() (+0x8007FBC/0x8007BD8)                       // група 0x400
```
`0x8007FBC(1)` / `0x8007FBC(0)` — встановлення/зняття **біта 1** слова
`*(u16*)0x2000000A` (пара «зайнято/вільно» навколо запису в flash; це **програмний
прапорець**, не RTOS-м'ютекс — див. §2.2). Парна `0x8007FCC` керує бітом 0 того
ж слова. Порожній виклик `0x80064C8`-parallel не використовується.

**Повний ланцюг зміни налаштування:**
```
зовнішній Modbus Master (FC6/FC10, рег. 0x2000..0x2093 / 0x3300.. / 0xFC00..)
   -> 0x80075E0 -> 0x80060EC -> setter 0x80094AA / 0x80090A8 / 0x8009452
   -> RAM-банки 0x20000414 / 0x494 / 0x514 / 0x544
   -> подія -> bit2..bit5 головної задачі
   -> 0x8006CDC / 0x66B0 / 0x6B0C / 0x6824
   -> 0x8008D40 -> flash 0x0803A000 / 0x0803C000 / 0x0803E000
```

Відповідне читання (FC3, ті самі регістри) іде **назад із RAM-банків**, але
`0x800467C`-гілка `0x8008A04` дозволяє прочитати параметр безпосередньо з flash.

### 7.2 Перевірки кадрів у слотах

```
0x8008C80: h = 0x100 / 0x1100, cap 0x40
0x8008880: h = 0x200 / 0x1200, cap 0x40  -> 0x800668C -> 0x8007F08
0x8008AA4: h = 0x300 / 0x1300, cap 0x18  -> 0x8006AE8 -> 0x8007FAC
0x8008944: h = 0x400 / 0x1400, cap 0x28, буфер 0x20000544 -> 0x8007F3C
```
Буфери слотів 1–3 = `0x20000494`. Довжина `3 … 0xFE`.
Контрольна сума `0x080084F6` = `Σ halfwords[0 … len-1] == halfwords[len]`,
де `len` — перше слово кадру і воно **входить у суму**;
якщо `len < cap`, хвіст добивається `*buf = cap` *(раніше)*.

### 7.3 `0x20000494` — «другий протокол»

Це і є буфер слотів 1–3. Його поля, які читаються напряму:
* `+4` (u16) — читає `0x08009AC8()`;
* `+6` (u16) — **адреса пристрою-сусіда**, читає `0x08009AA4()` і використовується
  в роутері `0x8007458` як допустима адреса приймача.

Тобто **другий протокол — це кадри, які приходять на канали 1..3 (slave)**,
адреса яких звіряється з `*(u16*)(0x20000494+6)` *(доведено для фільтра; сам формат
кадрів ще не вивчено)*.

### 7.4 Банки слотів у RAM — мапа адрес *(повністю доведено з коду `0x80069C0`)*

Ініціалізатор `0x080069C0` (єдиний викликач — `0x800728C`, стартовий блок) робить
**ровно 6 кроків**:

**1) `*(u16*)0x2000000A = 0`** + дві мутекс-подібні функції `0x8007FDC(1)`, `0x8007FCC(1)`.

**2) Обнулення чотирьох пар банків** (set1 = база, set2 = база + `0x180` — **робоча
копія**, саме вона йде в flash). Другий банк рахується як `r2 = r1 + 0x180`:

| set1 (видимий FC3/FC6/FC10) | set2 (робоча, у flash) | Розмір, u16 | Слоти |
|---|---|---|---|
| `0x20000414` | `0x20000594` | `0x40` | `0x100 … 0x13F` / `0x1100 … 0x113F` |
| `0x20000494` | `0x20000614` | `0x40` | `0x200 … 0x23F` / `0x1200 … 0x123F` |
| `0x20000514` | `0x20000694` | `0x18` | `0x300 … 0x317` / `0x1300 … 0x1317` |
| `0x20000544` | `0x200006C4` | `0x28` | `0x400 … 0x427` / `0x1400 … 0x1427` |

Межі в коді: `0x414`, `0x414+0x80=0x494`, `0x514`, `0x514+0x30=0x544` — **обидва
набори безперервні**: `0x20000414 … 0x20000714` (0x300 байт = 4 пари).

**3) Таблиця перекладу A — `0x20000114`, 0x100 записів (u16), `i = 0 … 0xFF`:**
```
i ∈ [0x00,0x40) -> 0x0100 + i          i ∈ [0x40,0x80) -> 0x10C0 + i  (= 0x1100..0x113F)
i ∈ [0x80,0xC0) -> 0x0180 + i          (= 0x200..0x23F)
i ∈ [0xC0,0x100)-> 0x1140 + i          (= 0x1200..0x123F)
```

**4) Таблиця B — `0x20000314`, 0x40 записів, `i = 0 … 0x3F`:**
```
i ∈ [0x00,0x18) -> 0x0300 + i          i ∈ [0x18,0x40) -> 0x03E8 + i  (= 0x400..0x427)
```

**5) Таблиця C — `0x20000394`, 0x40 записів, `i = 0 … 0x3F`** (`r2 = 0x20000414-0x80`,
`r3 = 0x13E8`):
```
i ∈ [0x00,0x18) -> 0x1300 + i          i ∈ [0x18,0x40) -> 0x13E8 + i  (= 0x1400..0x1427)
```

Три таблиці лежать **підряд**: `0x20000114 + 0x200 = 0x20000314`,
`0x20000314 + 0x80 = 0x20000394`, `0x20000394 + 0x80 = 0x20000414` — тобто рівно
до початку першого банку. Спільна таблиця A нумерує **всі** 0x100/0x1100/0x200/0x1200
слоти одним масивом; B і C розрізняють «основні» та «дзеркальні» (`0x3xx` vs `0x13xx`).

**6) Виклики нормалізації flash-сховищ:**
```
0x8005770()        // загальна перевірка/ініціалізація FMC
0x8004548()        // сховище A: 0x0803A000..0x0803BFFF, таблиця 0x20000114, scratch 0x200000F8
0x80046E4()        // сховище B: 0x0803C000..0x0803DFFF, таблиця 0x20000314, scratch 0x200000FA
0x8004880()        // сховище C: 0x0803E000..0x0803FFFF, таблиця 0x20000394, scratch 0x200000FC
...pop;  b.w 0x80056C0()   // хвостовий виклик
```
Кожен із трьох — **однакова клонована функція**: проходить по сторінці, звіряє
збережені ключі з таблицею перекладу, виявляє маркери `0xFFFF` (стираний) і
`0xEEEE`, за потреби **стирає/переписує сторінку** (`0x8004B78`/`0x8004B96`/`0x8004BB4`
= операція над сторінкою, `0x8004AD0`/`0x8004B08`/`0x8004B40` = гілка помилки,
`0x800467C`/`0x8004818`/`0x80049B4` = повторне читання, `0x8004DCC` = валідація).

**Диспетчер регістрів:**
```
0x8008A04(reg, 1, &out)  = ЧИТАТИ з flash:
   reg ∈ {0x100..0x13F, 0x200..0x23F, 0x1100..0x113F, 0x1200..0x123F} -> 0x800467C(reg,&out)
   reg ∈ {0x300..0x33F, 0x400..0x43F}                                  -> 0x8004818(reg,&out)
   reg ∈ {0x1300..0x133F, 0x1400..0x143F}                              -> 0x80049B4(reg,&out)
   інакше -> повертає 1 (не знайдено), *out лишається
   повертає 0 = знайдено

0x8008D40(reg, 1, &val)  = ПИСАТИ в flash (той самий switch):
   -> 0x80046C4 / 0x8004860 / 0x80049FC
```
Обидві викликаються **лише з чотирьох функцій збереження (§7.1) та з парсерів
кадрів `0x80084C0/0x8008880/0x8008944/0x8008AA4/0x8008C80`** (xrefs зібрані `tools/xref.py`).

### 7.5 Параметри у flash — три сховища *(ключова знахідка цієї сесії)*

Три **незалежні flash-сховища параметрів** (кожне — набір записів `{u16 value, u16 key}`,
key = номер слота; пошук іде **вниз від верху 4-КБ сторінки**, тобто останній запис перемагає):

| Сховище | База | Сторінки | Ключі (слоти) | Читання | Запис | Нормалізація (init) |
|---|---|---|---|---|---|---|
| **A** | `0x0803A000` | `0x0803A000`, `0x0803B000` | `0x0100…0x013F`, `0x0200…0x023F`, `0x1100…0x113F`, `0x1200…0x123F` | `0x800467C` | `0x80046C4` | `0x8004548` |
| **B** | `0x0803C000` | `0x0803C000`, `0x0803D000` | `0x0300…0x0317`, `0x0400…0x0427` | `0x8004818` | `0x8004860` | `0x80046E4` |
| **C** | `0x0803E000` | `0x0803E000`, `0x0803F000` | `0x1300…0x1317`, `0x1400…0x1427` | `0x80049B4` | `0x80049FC` | `0x8004880` |

Допоміжні: `0x8004A1C` / `0x8004A58` / `0x8004A94` = «яка сторінка зараз чинна»
(повертає номер сторінки або `0xAB` = порожня); операції над сторінкою
`0x8004B78` / `0x8004B96` / `0x8004BB4`; гілки помилки `0x8004AD0` / `0x8004B08` / `0x8004B40`.

Формат пошуку (`0x800467C(reg, out)`):
```
r0 = 0x8004A1C(0);  if (r0 == 0xAB) -> return 1       // 0xAB = «сторінка порожня»
r1 = 0x0803A000 + (r0<<12) + 2      // нижня межа
r2 = 0x0803AFFE + (r0<<12)          // верхня межа (початок пошуку)
while (r2 > r1) { if (*(u16*)r2 == reg) { *out = *(u16*)(r2-2); return 0; } r2 -= 4; }
return 1
```

**Повна заводська мапа значень, зчитана зі сховищ** (стан на момент запису прошивки).
Значення `0x13F` = `0x4051`, `0x23F` = `0xB16C` — **контрольні суми блоків**
(підтверджено `0x80084AC`, §7.1), а `0x100` / `0x200` / `0x300` / `0x400` —
**кількість записів у групі** (64 / 64 / 24 / 40):

| Слот | За замовчуванням | Припущене значення |
|---|---|---|
| `0x100` | 64 | |
| `0x101` | 3 | кількість пристроїв |
| `0x102…0x106` | 0 | |

## 8. CAN

### 8.1 Ініціалізація — `0x080061A8` *(раніше)*

```
0x8005EB8(0x719 / 0x603 / 0x604 / 0x605)      // годування CAN0 + GPIO
gpio_init(<port>, 0x48, 3, 0x100)              // AF push-pull
0x80054FA(0, sp)                               // фільтри: default ID 0x3FF -> 0x18
0x80054F2(CAN0, 2)
```
База `0x40006400`, літерали `0x8005318, 0x8006298, 0x8006478, 0x800648C`.

### 8.2 Передавання — **працює повністю** *(доведено)*

```
0x80062A0(ch, type)   -> формує кадри 0x351 / 355 / 356 / 359 / 35C / 35E
0x80064C8             -> пише TIxR (ідентифікатор)
0x80064DC             -> канальні реквізити
0x08004470(chan, frame)
    0x8004188()                      // критична секція
    якщо кільце порожнє і 0x8008494(0)==0 (TME0 вільна)
        -> 0x8006490()               // прямий запис у mailbox
    інакше
        -> 0x80042CE()               // у TX-кільце 0x20002E3C
    0x8004190()
```
ISR `0x80044D0` (CAN0_TX) вивільняє mailbox і витягує наступний кадр із кільця.

### 8.3 Приймання — **не використовується** *(ключовий висновок, доведено)*

* ISR `0x8004358` / `0x8004398` читають `CAN_RFIFO0/1` і викликають `0x800431E`
  (push у кільце), записуючи в кільце з базою **`0x20002E58`**.
* У мапі RAM `0x20002800 … 0x20004000` міститься лише 6 записів-літералів:
  SP ×2, TX-кільце ×2, **RX-кільце ×2** (`0x20002E3C` і `0x20002E58`).
* `bl 0x800431E` трапляється **тільки** в RX-ISR, `bl 0x80042A2` — **тільки** в TX-ISR.
* **Ніяка задача не викликає `0x8008494`-подібні читання RFIFO напряму, і ніхто не
  споживає `0x20002E58`.**
* Наслідок: `count = max = 0`, гілка «переповнення» → функція повертає 8 →
  **усі прийняті CAN-кадри відкидаються.**

Отже: **CAN використовується тільки на передавання** (стан інвертора/батареї на шину),
обробки вхідних CAN-повідомлень у цій прошивці **немає**.

### 8.4 Кадри, що відправляються — **повна таблиця** *(доведено в цій сесії)*

`0x080062A0(ch, type)` будує кадр на стеку у форматі
`{ u32 id; u8 payload[12] }` і викликає `0x80064C8(ch, frame, len)`:

| `type` | CAN ID | `len` | Payload |
|---|---|---|---|
| **1** | **0x351** | 8 | `u16[4]` = reg **0x100**, **0x102**, **0x103**, **0x101** (з `0x20001028`, див. §6.6) |
| **2** | **0x355** | 4 | `u16[0]` = **reg 0x110 / 10** (udiv), `u16[1]` = **100**, `u16[2]` = 0, `u16[3]` = 0 |
| **3** | **0x356** | 6 | `u16[0]` = **reg 0x10D × 6** (`(v + v*2) << 1 & 0xFFFF`), `u16[1]` = **reg 0x10C**, `u16[2]` = **(reg 0x11D + reg 0x11F) / 2**, `u16[3]` = 0 |
| **4** | **0x359** | 7 | байти, див. нижче |
| **5** | **0x35C** | 2 | `b0` = біт-поле з reg **0x105**, `b1..b7` = 0 |
| **6** | **0x35E** | 8 | **`'P' 'Y' 'L' 'O' 'N' 0 0 0`** = ASCII-рядок **`PYLON`** |

**`type = 4` → 0x359, детально:**
```
b0 = (reg0x107.bit5 ? 0x80:0) | (bit9 ? 0x10:0) | (bit8 ? 0x08:0)
   | (bit3 ? 0x04:0) | (bit2 ? 0x02:0)
b1 = (reg0x107.bit6 ? 1:0) + ((reg0x107 & ~0x33C) != 0 ? 8:0)
     // 0x33C = біти {2,3,4,5,8,9} -> «інші біти» дають +8
b2 = (reg0x109.bit5 ? 0x80:0) | (bit9 ? 0x10:0) | (bit8 ? 0x08:0)
   | (bit3 ? 0x04:0) | (bit2 ? 0x02:0)
b3 = (reg0x109.bit6 ? 1:0)
b4 = reg0x114                     // 0x8009B94
b5 = 0x50  'P'      b6 = 0x4E 'N'      b7 = 0
```

**`type = 5` → 0x35C, детально:**
```
b0 = (reg0x105.bit7 ? 0x80:0) | (bit6 ? 0x40:0) | (bit4 ? 0x20:0)
   | (bit5 ? 0x10:0) | (bit3 ? 0x08:0)
b1..b7 = 0
```

**Планувальник — `0x08007754(ch, period, sub)`** *(повністю доведено)*:
```
if (ch != 0) return;                       // працює ТІЛЬКИ для каналу 0
if (0x8005BF4() == 0) return;              // канал не готовий
r0 = 0x20000088
counter  = ++byte[0x20000089];             // лічильник періоду
if (counter < period) {
        if (byte[0x2000008B] == 0) return;      // ще не почали
} else {
        byte[0x20000089] = 0;
        byte[0x2000008B] = 1;                   // type := 1
        byte[0x20000088] = 1;
}
subcnt = ++byte[0x2000008A];
if (subcnt >= sub) { byte[0x2000008A] = 0; byte[0x2000008B]++; }   // type++
type = byte[0x2000008B];
tail -> 0x80062A0(ch, type)                      // type > 6 -> нічого не шле
```
Виклик із головної задачі: **`0x8007754(0, 50, 5)`** → тип ротується
`1,2,3,4,5,6,(7..13 → мовчки)`, потім скидається в 1 через 50 тиків.
Тобто **усі шість CAN-ID відправляються по черзі з періодом ≈ 50 тиків на повний цикл**.

Каркас кадру, який реально йде в mailbox (`0x80064C8`):
`ldrh r3, [r1]` → перше слово = CAN-ID (0x351…0x35E), далі `lsls r3, #0x15` —
це ознака **standard ID** (не extended).

Планувальник, який запускає все це, стартує в `bit0` головної задачі:
```
0x8007A64(0,2); 0x8007A64(1,2); 0x8006590(0,750);
0x80070A8(0,50);                                  // Modbus-опитування BMS
0x8006DE8(100); 0x80067BC(100); 0x8006C14(100); 0x8006930(100);
0x8006C80(9000); 0x8007754(0,50,5)                // CAN-ротація
```
Усі викликачі цих планувальників знайдені через `tools/xref.py`; чотири з них
(`0x8006DE8`, `0x80067BC`, `0x8006C14`, `0x8006930`) **викликаються саме з `bit0`**
головної задачі, `0x80062A0` — тільки хвостовим викликом із `0x8007754`.

## 9. Визначення типу виробу — `0x08007700` *(доведено)*

```
0x8007FCC(1);  0x8008094(0);  0x8008FA8(0x32);
r0 = 0x8008FA8(...)   -> якщо 7 -> тип 7;  якщо 9 -> тип 9
r0 = 0x8008F7C()      -> якщо 7 -> 7;      якщо 9 -> 9
r0 = 0x8008EDC(0x0F)  -> якщо 7 -> 7;      якщо 9 -> 9;  якщо 6 -> 6
інакше -> 1
*0x200000FE = тип   // 1, 6, 7 або 9
```
`0x8008FA8` / `0x8008F7C` / `0x8008EDC` — геть різні «прочитай щось і поверни 7/9/6»,
що виглядає як **зчитування ID з EEPROM/пристрою по шині** *(ймовірно)*.

`0x200000FE` потім керує:
* шаблоном LED у `0x800737C` (§2.3),
* диспетчером команд задачі 0 (§2.2),
* умовою в головній задачі `0x8008E68() ∉ {1,2,3}` — `0x8008E68()` читає `byte[0x20000026]`.

## 12. Відкриті питання (що ще не з'ясовано)

**Знято в цій сесії:**

* ~~**Яке джерело живить слоти 0x100 … 0x427?**~~ → **flash-сховища
  `0x0803A000` / `0x0803C000` / `0x0803E000`** (§7.5), повна заводська мапа значень
  зчитана. Слоти = параметри налаштувань + їх віддає RS485-слейв через FC3.
* ~~**Що роблять `0x800605A` і `0x80060EC`**~~ → повністю розібрано (§6.5):
  побудова відповідей FC3 і FC6/FC10 із чотирма гетерами й трьома сеттерами.
* ~~**Таблиця CAN-кадрів 0x351…0x35E**~~ → повна таблиця перетворень у §8.4,
  включно з `0x35E = "PYLON"` і планувальником `0x8007754(0,50,5)`.
* ~~**Хто і коли пише в банки `0x20000414..`**~~ → ланцюг повністю доведено (§7.1):
  Modbus FC6/FC10 → RAM-set1 → подія → `bit2..bit5` → `0x8006CDC/66B0/6B0C/6824`
  (копія set1→set2, контрольна сума в останній слот) → `0x8008D40` → flash.
* ~~**Семантика `0x8008A04`**~~ → `0 = знайдено`, `1 = не знайдено`;
  `0x8008D40` — запис того самого регістра в flash (§7.4).
* ~~**Bootloader**~~ → розібрано в §13: магія `G5RC` лежить у **app-зоні за
  `0x08004150`**, стирання йде тільки до `0x08033FFF`, параметрові сторінки
  `0x0803A000..0x0803FFFF` **зберігаються при оновленні прошивки**.
* ~~**Гілки диспетчера задачі 0**~~ → повна таблиця в §2.2; `case 9 = 0x8008418`
  = ввід у режим прошивання (§13.8).
* ~~**Семантика `0x80084AC`**~~ → **`1 = контрольна сума збігається`**, `0 = розбіжність`;
  `qty = set2[0]` = кількість записів групи; `0x8006574` знімає прапорець
  `0x2000005A.11`, `0x8007BAC` його ставить (§7.1).
* ~~**`0x80056E8` / `0x8005770` / `0x80056C0`**~~ → `fmc_page_erase` / `fmc_unlock` /
  `fmc_lock` (звірено з `gd32f30x_fmc.h`, §13.8).
* ~~**Ініціалізація UART**~~ → `0x80082FC` = USART0 (PA9/PA10, 9600), `0x8008388`
  = UART4 (PC12/PD2, 9600), обидва з `0x8007894` (§2.2, §4).

**Лишається:**

1. **Гілки задачі 0 (пріоритет ⑤) — рамку й усі гетери розібрано (§2.2), але
   значення самої логіки лишилося:** для кожної гілки не відомо, **навіщо** вона
   чекає біти 1/2/3/4/5/6/7/9/10 і що означає перехід «стан → команда»;
   невідомий **писець лічильника `0x20000084`** (`0x800903C()`, пороги 30 і 300) —
   прямих літералів `0x20000084`/`0x2000004C+0x38` у коді немає, тож він пишеться
   через обчислений вказівник.
2. **Парсери «другого протоколу»** `0x80084C0` / `0x8008880` / `0x8008944` /
   `0x8008AA4` / `0x8008C80` — відомо лише, що вони викликають `0x8008A04`/`0x8008D40`
   (тобто читають/пишуть ті самі параметри), і повертаються в `0x800668C`/`0x8006AE8`/`0x8007F08`/`0x8007F3C`/`0x8007FAC`.
3. **Точний формат кадрів «другого протоколу»** (слоти 1–3, буфер `0x20000494`),
   включно з полем `+6` (адреса пристрою-сусіда).
4. **Піни LED/DE не позначені на схемі** — підтверджені лише за кодом:
   PC13, PB0, PB1, PC5 (§2.3). Варто звірити з платою.
5. **UART3** — база й літерали є, GPIO-ініціалізація не знайдена.
6. **Ідентифікація `0x8008FA8`/`0x8008F7C`/`0x8008EDC`** — припускається EEPROM/ID-зчитування.
7. Частину регіонів пропускає `radare.py` (рекурсивний обхід) — для повноти варто
   прогнати лінійний дизасембл `dumps/combobox_bkp_40000.asm`.

## 13. Bootloader `0x08000000 … 0x08003FFF` *(доведено в цій сесії)*

### 13.1 Векторна таблиця

```
0x08000000: 0x200004B8     початковий SP bootloader'а
0x08000004: 0x08000165     Reset_Handler  (-> 0x08000164)
0x08000008: 0x080006F7     NMI
0x0800000C: 0x080001B3     HardFault    (-> 0x080001B2, `b .`)
0x08000010: 0x080006F5     MemManage
0x08000014: 0x080001AD     BusFault     (-> 0x080001AC, `b .`)
0x08000018: 0x08000749     UsageFault
```
`Reset_Handler 0x08000164` → `blx 0x080006F8` (`.data/.bss`-init), далі
**таблиця конструкторів** `0x08001418 … 0x08001438` (2 записи по 0x10 байт:
`r0,r1,r2, cb` → `blx cb`) і `bl 0x08000158`.

### 13.2 Магія валідності застосунку — `0x080003CC`

```
r0 = *(u32*)(0x08004000 + 0x150)        // тобто *(u32*)0x08004150
r1 = 0x43523547                          // little-endian 'G','5','R','C' = "G5RC"
if (r0 == r1) return 0;   // валідно
else           return 1;   // не валідно -> завантажувати
```
**Магія живе у flash застосунку за `0x08004150`** (у бінарнику її дійсно видно:
`bytes 0x4150..0x4153 = 47 35 52 43`). Літеральні копії `G5RC` у bootloader'і
(`0x080003E4`, `0x08000B10`) — це **pool-слови**, а не код.

### 13.3 Стирання — що і куди

| Функція | Що робить |
|---|---|
| `0x0800090C` | FMC unlock |
| `0x0800085C` | FMC lock |
| `0x08000884(addr)` | **стирання однієї сторінки 2 КБ**, що містить `addr` (CTRL: BYTER→ADDR→PER→зняти BYTER). Перевірка `*(u16*)0x1FFFF7E0` (flash size) і межі `0x0807FFFF` |
| `0x08000768` / `0x080007A8` | гілки «звичайна» / «option bytes» |
| `0x080003E8` | **стирає сторінку `0x08004000`** (у ній лежить `0x08004150`) → **зняття магії `G5RC`** |
| `0x080001B4` | **стирає весь образ застосунку**: `for (a = 0x08004000; a <= 0x08033FFF; a += 0x800) 0x08000884(a)` |

**Ключовий висновок:** діапазон стирання — **`0x08004000 … 0x08033FFF` (192 КБ)**.
Отже при оновленні прошивки **зберігаються**:
* `0x08034000 … 0x08039FFF` (24 КБ, вільно/резерв)
* **`0x0803A000 … 0x0803FFFF` (16 КБ) — усі три flash-сховища параметрів (§7.5)**

Тобто **налаштування переживають перепрошитування** — це і є призначення
«міграційних» записів `{value, key}`.

### 13.4 Запуск застосунку — `0x08000AEC`

```
r4 = 0x08004000                       // літерал 0x08000B0C
r0 = *(r4 + 4)                        // app Reset_Handler (vec1 = 0x08004169)
r1 = *(r4)                            // app initial MSP  (vec0 = 0x20003278)
r1_save = 0x20000000;  store r0 into +0x14 / +0x18      // лог для діагностики
msr msp, r1                           // переключити стек
blx r0                                // -> застосунок
```
Попередньо деініціалізується периферія: `0x08001390(0x40005000)` — вимкнення
**UART4**; аналогічно для інших.

### 13.5 Канали зв'язку bootloader'а

Літерали баз у регіоні `0x08000000 … 0x08004000`:

| Периферія | База | Сайти |
|---|---|---|
| **USART0** | `0x40013800` | `0x8000548`, `0x80005FC`, `0x8000B18`, `0x8001110` |
| **USART2** | `0x40004800` | `0x80005F8` |
| **UART3** | `0x40004C00` | `0x8000B1C`, `0x800119C`, `0x8001328`, `0x8001388` |
| **UART4** | `0x40005000` | `0x8000B20`, `0x800122C` |
| FMC | `0x40022000` | ×6 |
| RCU | `0x40021000` | ×8 |
| GPIOA/B/C | `0x40010800` / `0x40010C00` / `0x40011000` | ×3/×1/×7 |
| IWDG | `0x40003000` | ×3 |

Драйвер UART (`0x080013A4(uart, bit)` = читання біта регістра `STAT`),
`0x08001330(uart, data)` = запис `DATA` (9 біт), `0x0800130C(uart, apb, baud)` =
формування `BRR` за формулою `(apb + baud/2) / baud` → запис у `[uart+8]`.

`0x080005A4` — **полінг двох UART одночасно**: `state[+0x1C]` перемикається між
`USART0 (0x40013800)` і `USART2 (0x40004800)`; для активного каналу
`0x80013A4(uart, 5)` (біт **RXNE**), `0x08000C86(byte)` → обробка,
байт кладеться в `0x20000028[len]`.

### 13.6 Стан і вхідні умови (RAM `0x20000000`, структура ~0x30)

```
+0x01  byte  «зачинено»/стан поновлення
+0x02  byte  лічильник / покажчик
+0x03  byte  поточний канал: 1 = USART0, 3 = USART2
+0x04  byte  XOR-сумка фрейма
+0x05  byte  останній байт (контрольна)
+0x06  byte  покажчик у буфері
+0x07  byte  **код із PC0..PC3** (активний низький: PC3→+8, PC2→+4, PC1→+2, PC0→+1)
+0x08  byte  лічильник тактів (межа 0x8C)
+0x0B  byte  «кнопка/вхід» таймаута (межа 5)
+0x10  u16   лічильник входу (межа 0x32 = 50)
+0x12  u16   глобальний лічильник (межа 0x48F5 = 18677)
+0x1C  ptr   **поточний UART-периферійний базис** (USART0 ↔ USART2)
+0x20  u32   адреса запису
+0x24  u32   база блоку
0x20000028    буфер фреймів, 0x8C = 140 байт
```

`0x08000430` (init): `uart = USART0`, обнуляє `0x20000028[0..0x8B]`, читає
**PC0..PC3** (`0x08000A5C(GPIOC, mask)` для масок 8,4,2,1) у `state[+7]`.

`0x08000558` (такт): кожні **0x48F5 (18677)** тиків читає **PA8**
(`0x08000A5C(GPIOA, 0x100)`); якщо `state[+0x10] >= 50` → дія на **PC9**
(`0x080009B8(GPIOC, 0x200)`). Тобто **утримувана кнопка на PA8 ≈ входить у режим
оновлення/скидання** *(ймовірно)*.

### 13.7 Послідовність оновлення — `0x08000634`

```
0x08000634: 0x08000430()      // init стану, USART0, читання PC0..PC3
0x08000638: 0x08000658()      // GPIO/RCU: PC13 (0x2000), PC9 (0x200) — LED стану
0x0800063C: state[+1] = 1     // «почали оновлення»
0x08000642: 0x08000994()      // IWDG reload
0x08000646: 0x080003E8()      // стерти сторінку 0x08004000 -> зняти магію G5RC
0x0800064A: 0x080001B4()      // стерти 0x08004000..0x08033FFF
0x0800064E: 0x080001E8()      // цикл прийому/запису образу
```

Прийом (`0x080001E8`): стан `0x20000000`, буфер `0x20000028`, довжина
`state[+2]`, порівняння з межею **0x8C (140)**, XOR-контрольна сума
(`eors r2, r3; strb r2, [r4, #4]`), дзеркальна копія у `state[+0x20]` з
додаванням `state[+0x24]`. Рішення «тихо стартувати застосунок» приймається
за таймаутом, коли `state[+0x08] >= 5` (після `subs r0, #5`).

### 13.8 Як застосунок сам заходить у режим прошивання — `0x08008418` *(нове)*

Диспетчер задачі 0, `case 9` (гілка `0x8008418`), викликається після
`bit9` — його шлють `0x800748C` (магічний кадр `G5RC` + `buf[6]==0x0D`) і
`0x8007A10` (звірка адреси) — §2.4. Код:

```c
for (i = 0; i < 25; i++) 0x800500C(1);   // дати системі доробити поточне
0x8005770();                             // FMC_KEY0 = 0x45670123 / 0xCDEF89AB  -> fmc_unlock()
0x80056E8(0x08004150);                   // PER=1, ADDR=0x08004150, START=1     -> fmc_page_erase()
0x80056C0();                             // CTL0 |= LK                          -> fmc_lock()
r1 = 0x08000000;                         // векторна таблиця BOOTLOADER'а
r0 = *(r1 + 4);                          // = 0x08000165  bootloader Reset_Handler
*(0x200000B4 + 0x0C) = r0;  *(0x200000B4 + 0x10) = r0;   // діагностика
msr msp, *(r1);                          // SP = 0x200004B8
blx r0;                                  // -> ПЕРЕХІД У BOOTLOADER
for (;;) ;
```

**Що відбувається насправді:** `0x08004150` лежить у **першій сторінці застосунку
`0x08004000…0x080047FF`**, тож `fmc_page_erase(0x08004150)` **стирає разом із
магією `G5RC` і векторну таблицю застосунку**. Далі код завантажує початковий SP
і Reset_Handler **з `0x08000000`** (тобто з bootloader'а) і виконує їх.

У bootloader'і `0x080003CC` порівнює `*(u32*)0x08004150` з `0x43523547` (`G5RC`);
після стирання там `0xFFFFFFFF` → **«застосунок невалідний»** → bootloader іде в
`0x08000634` (секція «стери весь образ і приймай новий»). Отже:

> **`G5RC` на RS485 = «ввід у режим прошивання / firmware update».**
> Це єдиний спосіб потрапити в bootloader, бо без стирання магії bootloader
> одразу ж стрибає назад у застосунок (`0x08000AEC`).

`0x80056E8(addr)` підтверджено як **стирання однієї сторінки 2 КБ** за заголовком
`gd32f30x_fmc.h`: `FMC_CTL0_PER = BIT(1)`, `FMC_CTL0_START = BIT(6)`,
`FMC_CTL0_LK = BIT(7)` — точно збігається з `orr #2` / `orr #0x40` / `orr #0x80`.
Сторінкові хелпери `0x8004B78` / `0x8004B96` / `0x8004BB4` (§7.5) викликають той
самий `0x80056E8`.

## 14. Склад папки `original_firmware/`

```
original_firmware/
├── ORIGINAL_FIRMWARE.md              # цей документ
├── combobox_bkp_40000.bin            # ОРИГІНАЛЬНА заводська прошивка (256 КБ)
├── dumps/
│   └── combobox_bkp_40000.asm        # лінійний Thumb-дамп (5.3 МБ)
└── tools/
    ├── radare.py                     # основний дизасемблер (дерево викликів + периферія)
    ├── dump.py                       # друк діапазону адрес (+ raw fallback)
    ├── ctx.py                        # контекст навколо адреси
    ├── disasm.py                     # мінімальний дизасембл
    ├── recon.py                      # первинна розвідка
    ├── xref.py                       # пошук прямих викликів (b/bl/blx) до адреси
    ├── periph_report.txt             # звіт периферійних літералів (генерується radare.py)
    └── db.json                       # база інструкцій/викликів/xrefs (генерується radare.py, 7.8 МБ)
```

Скрипти в цій папці вже переведені на **відносні шляхи** (шукають `.bin` поруч),
тобто папка `original_firmware/` самодостатня й не залежить від тимчасових каталогів.

**`tools/xref.py`** — швидкий інструмент для розв'язування викликів (пропускає
прямий рекурсивний обхід `radare.py`):
```bash
cd original_firmware/tools
python3 -c "import xref; xref.scan(0x80062A0)"   # -> [(site, 'bl'|'b'|'blx'), ...]
```
Працює по лінійному проходу по секції `.text`, тож знаходить і не-вершинні
виклики (хвостові `b.w`, виклики всередині циклів). Один виклик ≈ 4 с.

> **Примітка для git:** у кореневому `.gitignore` є рядок `combobox_bkp_40000.bin`
> (без шляху), тому бінарник у будь-якій підпапці ігнорується — це свідомо.
> `dumps/*.asm` (5.3 МБ) та `tools/db.json` (8 МБ, за бажанням) варто або не
> додавати до коміту, або додати окремий рядок у `.gitignore`.
