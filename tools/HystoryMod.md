## 2026-11-10 — Один отключённый АКБ из двух: «немає відповіді 0xNN» вместо «bad response header»

- **Файлы:** `tools/bms_web3.py`, `tools/bms_webX.py`
- **Было:** при отключении одного АКБ из двух быстрый опрос
  (`_poll_active` / `active_step`) писал в `err` сырой текст исключения
  `bad response header ...`. Если отключить оба АКБ, следующий полный скан
  менял сообщение на `немає відповіді 0xNN` — отсюда «сначала
  bad response header, затем немає відповіді».
- **Стало:** быстрый опрос сразу пишет `немає відповіді 0xNN` — то же
  сообщение, что и полный скан. Один отключённый АКБ из двух больше не
  показывает протокольную ошибку; второй АКБ продолжает опрашиваться,
  порт остаётся подключённым (`COMx @ 9600`, без `No Dongle`).
- **Проверки:** `py_compile`, `--selftest` обоих (добавлен сценарий «две АКБ,
  одна отключена»: живая остаётся online, мёртвая получает
  `немає відповіді 0x02`, `active_addrs == [1]`), harness'ы loop-уровня,
  `node --check`.
- **Откат:** правка минимальная (две строки `err = ...`), откат вручную.

## 2026-11-10 — OFFLINE в поле «Стан» карточки АКБ (оба скрипта)

- **Файлы:** `tools/bms_web3.py`, `tools/bms_webX.py`
- **Было:** при потере донгла или обрыве кабеля к АКБ поле «Стан» в карточке
  АКБ показывало нейтральное `—`. В `bms_webX.py` при этом рядом с
  заголовком «Батарея N» висела отдельная плашка `OFFLINE`, а в
  `bms_web3.py` такой плашки не было — вид отличался.
- **Стало (оба скрипта):** плашка `OFFLINE` перенесена в поле «Стан»
  (класс `pill bad`). В `bms_webX.py` плашка `conn_<id>` рядом с
  «Батарея N» удалена; карточка сразу рендерится с `OFFLINE`, если АКБ
  офлайн. При следующем успешном опросе `updateBmsUI()` /
  `renderPackDetail()` возвращают реальный статус (`Standby`,
  `Charging`, ...). Сводная таблица в `bms_web3.py` уже показывала
  `OFFLINE` в колонке «Стан» — не менялась.
- **Status (0025):** при офлайне лампы карточек Status (0025),
  Warning (0026), Protection (0027) и Error (0028) гасятся, а сырой hex
  очищается в `—`. Раньше после обрыва кабеля в карточке Status (0025)
  оставалась гореть лампа `Standby` (и могли оставаться Warning/Protection/
  Error), потому что UI перерисовывал последние полученные данные. Теперь
  при следующем успешном опросе лампы и hex возвращаются.
- **Проверки:** `py_compile`, `--selftest`, живые harness'ы loop-уровня,
  `node --check` обоих, mock `/api/data` обоих, браузерный тест
  Playwright: до обрыва — реальный статус и одна горящая лампа, после —
  `Offline`, все лампы погашены, hex `—`; после восстановления — снова
  реальный статус.
- **Откат:** `tools/bms_webX.py.bak-20261110_124908`,
  `tools/bms_web3.py.bak-20261110_124908` (до COM-унификации; UI-правка

## 2026-11-10 — Единый COM/offline-алгоритм в bms_web3.py и bms_webX.py

- **Файлы:** `tools/bms_web3.py`, `tools/bms_webX.py`
- **Было (bms_web3.py):** после обрыва кабеля RS485 к АКБ (USB-донгл
  остаётся) скрипт сначала показывал `bad response header`, а затем
  уходил в `No Dongle: немає відповіді від АКБ`. Причина — фолбэк в
  `active_step()`: если все известные АКБ замолчали, порт считался
  потерянным и сбрасывался.
- **Было (bms_webX.py):** тот же фолбэк в `_poll_active()` срабатывал, но
  был почти незаметен: на следующем цикле порт открывался снова, а
  `_scan_all()` перезаписывал `err` на `немає відповіді 0xNN`. То есть
  рабочий порт при обрыве кабеля всё равно зря закрывался/открывался.
- **Стало (оба скрипта):**
  - фолбэк «все АКБ замолчали → потеря донгла» удалён;
  - реальная потеря порта — только `_port_gone()` /
    `_port_missing_now()` / `_maybe_switch_port()`;
  - при обрыве кабеля карточка показывает `OFFLINE` и
    `немає відповіді 0xNN`, заголовок остаётся на порту (`COMx @ 9600`),
    плашка «Стан» — `—`;
  - `_scan_all()`/скан в `bms_web3.py` одинаково пишут причину по АКБ;
  - `loop()`/`active_loop()` имеют одинаковый внешний перехват ошибок:
    закрыть серийный хэндл, сбросить порт только если он исчез,
    пометить АКБ offline, пауза 1 с;
  - пассивный режим одинаково пишет `немає кадрів 0xNN >N с` и вызывает
    `_mark_offline()` при ошибке порта.
- **Старт порта (bms_webX.py):** интерактивный выбор из нескольких донглов
  убран, теперь тот же тихий `find_usb_rs485_port()`: FTDI → CH340/CH341 →
  CP210x → Prolific → generic; внутренние COM1/ACPI, Bluetooth и debug
  игнорируются; `--port` по-прежнему главнее. `DEFAULT_PORT` проверяется
  через `os.path.exists`, как в `bms_web3.py`.
- **Детект USB-serial:** `_looks_like_usb_serial()` теперь учитывает и имя
  устройства, и `ttyUSB`/`ttyACM`/`usbserial` (Linux/macOS); `acpi`
  добавлен в `_port_ignored()`.
- **Диагностика `open()`:** в `bms_web3.py` добавлен тот же `_open_error()`,
  что и в `bms_webX.py` (занятый порт / порт не найден / прочее). Тексты
  локализованы, логика одинаковая.
- **Сверка:** общие функции `_port_info_dict`, `_looks_like_usb_serial`,
  `list_ports_report`, `_port_ignored`, `_port_rank`,
  `choose_port_from_rows`, `autodetect_port_silent`, `_chip_label`,
  `find_usb_rs485_port`, `_port_gone`, `_port_missing_now`, `_drop_serial`
  теперь побайтово идентичны в обоих файлах; `_maybe_switch_port()`
  отличается только языком сообщений, `_mark_offline()` — только именем
  поля (`ok` vs `online`).
- **Проверки:** `py_compile` обоих, `--selftest` обоих (в `bms_webX.py`
  добавлен сценарий «кабель выдернут, донгл на месте»), живые harness'ы
  loop-уровня для обоих, `--allow-no-port`/`--mock`/`--port` для
  `bms_webX.py`, mock `/api/data`, `node --check` обоих.
- **Откат:** `tools/bms_webX.py.bak-20261110_124908`,
  `tools/bms_web3.py.bak-20261110_124908`; более ранний —

## 2026-11-09 — Отказ от автопереключения на «лучший» донгл

- **Файл:** `tools/bms_webX.py`; отчёты `comPortDetect.html`,
  `DetectDongleWebX.html`
- **Было:** `_maybe_switch_port()` раз в 5 с сравнивал приоритеты и
  переключал шину на FTDI/CH340/CP210x, если такой донгл появлялся при
  уже работающем generic USB-serial.
- **Почему убрали:** при двух USB-RS485 на разные АКБ скрипт самопроизвольно
  переезжал на «более приоритетный» порт, хотя текущий работал. Смена
  порта должна быть целенаправленной.
- **Стало:**
  - приоритет используется только при выборе порта, когда он ещё не
    открыт (старт или повторный автодетект);
  - `_maybe_switch_port()` проверяет только: порт исчез или перестал быть
    USB-serial. Работающий порт не заменяется;
  - чтобы перейти на другой донгл: выдернуть текущий (порт исчезнет и
    найдётся заново) или запустить с `--port COMx`;
  - `selftest()` и интеграционный сценарий проверяют, что второй донгл
    не заменяет работающий порт.
- **UI при потере порта:** добавлен `_mark_offline(reason)` — все известные
  АКБ получают `ok=false` и причину в `err`. В карточке бейдж становится
  `OFFLINE`, плашка «Стан» — нейтральное `—` вместо зелёного `Standby`,
  светодиоды статусов гаснут (класс `offline`). После восстановления
  первый успешный опрос снова ставит `ok=true`.
- **Откат:** `tools/bms_webX.py.bak-20261109_131725`

## 2026-11-08 — Запуск без USB-RS485 донгла (D + C, re-autodetect)

- **Файл:** `tools/bms_webX.py`; отчёт `DetectDongleWebX.html`
- **Было:** если автодетект не находил USB-RS485, `main()` печатал ошибку
  и возвращал код `2` — веб-сервер не создавался, страница была недоступна.
  Циклы повторяли `open()` только для уже известного имени порта, поэтому
  пустой `port=""` не мог открыться никогда.
- **Стало:**
  - ключ `--allow-no-port`: при отсутствии порта сервер всё равно стартует;
  - `BmsBus(auto_port=...)`: в auto-режиме пустой порт переоткрывается
    с повторным автодетектом каждые `PORT_RETRY_S = 3 с`;
  - тихий выбор порта без `input()`: FTDI → CH340/CH341 → CP210x →
    Prolific → прочий USB-serial; внутренний COM1/ACPI, Bluetooth и
    debug в авто-режиме игнорируются (иначе COM1 занимал бы шину и
    мешал подключению донгла позже);
  - `_maybe_switch_port()` раз в `PORT_RESCAN_S = 5 с` сбрасывает
    выбранный не-USB порт или порт, которого больше нет в системе;
    работающий порт не заменяется; явный `--port` не трогает;
  - `_port_missing_now()`: если порта больше нет в списке устройств
    (USB выдернули), хэндл принудительно закрывается и `port=""` — даже
    если Windows оставил `is_open == True` (иначе повторное включение
    донгла не подхватывалось);
  - `_port_gone()` расширен кодами Windows/RU (`clearcommerror`,
    `write/read failed`, `the parameter is incorrect`, `отказано в доступе`
    и т.п.); занятый порт по-прежнему повторяется по имени;
  - `_poll_active()` при исчезновении всех известных АКБ сбрасывает
    устаревший хэндл — запасной путь, если список портов ещё не обновился;
  - `_drop_serial()` закрывает и забывает хэндл при ошибке;
  - явный `--port` не подменяется автодетектом;
  - UI: красный pill «No Dongle» (класс `pill bad`, как у «No server»),
    в подстроке режима — порт/`MOCK`/`No Dongle`;
  - `snapshot()`: `port`, `port_source`, `port_connected`, `mock`, `baud`;
  - `selftest()`: приоритет портов, игнорирование COM1, сохранение
    работающего порта при появлении второго донгла, пустой список,
    `open()` без донгла, подхват найденного порта, сброс «мёртвого»
    хэндла после выдёргивания (serial подменяется фейком).
- **Причина:** донгл может быть подключён позже запуска (через 1–5 минут);
  сервер должен быть доступен сразу, а подключение — происходить само.
- **Проверки:** `py_compile`, `--selftest`, `node --check`,
  старт без донгла с принудительной ошибкой автодетекта (код 0,
  `port=""`, «No Dongle»), строгий режим без флага (код 2),
  сценарий «только COM1» (COM1 игнорируется, после вставки CH340
  выбирается COM5), сценарий «выдернули/вставили» (порт исчез →

## 2026-11-04 — Единая схема CSV: порядок колонок без смещения

- **Файл:** `tools/bms_web3.py`
- **Было:** заголовок и данные собирались двумя независимыми списками.
  Перенос колонки только в `build_log_header()` сдвигал значения относительно
  заголовка (например, `Serial`, перенесённый в конец, смещал все поля после
  `addr`).
- **Стало:** `log_columns()` — единственный источник порядка колонок.
  `build_log_header()` возвращает этот список, а `build_log_values()` собирает
  значения по именам и выдаёт их в порядке `log_columns()`:
