Алгоритм записи CSV-лога
Alarm / State / Work — версия 3.5

Руководство перед реализацией. Описывает целевое поведение tools/bms_web3.py и tools/bms_webX.py. Оба скрипта должны работать одинаково; различия допустимы только в языке сообщений и именах полей модели данных (ok / online).

Ключевое решение: весь регистр 0025 считается регистром состояния BMS и пишется как State. Alarm формируется только по 0026 (Warning), 0027 (Protection), 0028 (Error) и температуре. Одновременно могут быть записаны две независимые строки: Alarm и State.

1. Назначение и область

CSV-лог — это телеметрия АКБ с отметкой типа строки в колонке Log. Он должен решать две задачи одновременно:

  • Анализ телеметрии — периодические полные срезы (профиль Work).
  • Журнал событий — изменения состояния BMS и аварийных регистров (профиль «Лише події», строки Alarm и State).

Оба профиля могут быть включены одновременно и пишут в один файл каждой АКБ. Событийные строки не заменяют и не сдвигают плановую строку Work: если событие и Work совпали в одном цикле, в файл попадают две или три строки с одинаковым временем.

Документ — руководство, а не описание текущего кода. Текущая реализация будет приведена к этому алгоритму следующим шагом. Все примеры ниже — целевые.

2. Регистры и термины

ОбозначениеРегистрСмыслТип события
S0025 Status / режим BMS: 0x00 Standby, 0x01 Charging, 0x02 Discharging, 0x04 Protect, 0x08 Charging Lmt, бит 0x8000 Heating. State — любое изменение
W0026 Warning: предупреждения BMS. Alarm
P0027 Protection: срабатывания защит. Alarm
E0028 Error: ошибки BMS. Alarm
Tпроизводное Температура Temp_Max_C: высокий порог >= 45.0 °C, низкий <= 0.0 °C. Alarm
Work— Периодический полный срез телеметрии. Work

Protect — это режим, а не отдельный аварийный регистр. Значение 0x04 в 0025 означает, что BMS находится в состоянии защиты. Причина защиты находится в 0027. Поэтому:

  • вход в Protect и выход из него — это State;
  • срабатывание/снятие самой защиты — это Alarm по 0027.

3. Профили записи

ПрофильUIЧто пишетКогда пишет
«Лише події» cfg_alarm, JSON alarm Alarm и State При изменении подписи состояния. Без изменений — ничего.
Анализ / тест комірок cfg_work, JSON work Work Периодически, каждые work_interval секунд (по умолчанию 5 с, минимум 1 с, максимум 3600 с).

Оба профиля независимы. Событийные строки дополнительные: они не отменяют и не переносят Work. Если в одном цикле есть событие и наступил Work, пишутся все строки, каждая со своим Log.

4. Подпись состояния

Для обнаружения изменений используется кортеж из шести элементов:

sig = (
    status,       # 0025, целое 0x0000..0xFFFF
    warning,      # 0026
    protection,   # 0027
    error,        # 0028
    temp_high,    # bool: Temp_Max_C >= 45.0
    temp_low,     # bool: Temp_Max_C <= 0.0
)

Последняя записанная подпись хранится в alarm_sig. Несмотря на имя, это подпись Alarm & State: она покрывает и аварийные регистры, и регистр состояния. Имя оставлено для совместимости и документируется в коде.

Подпись меняется, если изменился хотя бы один элемент. Сравнение всегда идёт с предыдущим опросом, а не с предыдущей событийной строкой:

prev = state["alarm_sig"]   # или st["alarm_sig"] в bms_web3.py
sig  = _alarm_signature(parsed)

5. Классификация Alarm / State

Что изменилосьСтрокаПояснение
0025 — любое изменение, включая вход/выход из Protect, бит Heating и неизвестные значения State Это регистр состояния BMS.
0026 Warning изменился Alarm Появление, изменение или снятие предупреждения.
0027 Protection изменился Alarm Появление, изменение или снятие защиты.
0028 Error изменился Alarm Появление, изменение или снятие ошибки.
Температура пересекла порог 45 °C или 0 °C Alarm В любую сторону, включая возврат в норму.
Одновременно изменились 0026/0027/0028/T и 0025 Alarm + State Две независимые строки с одинаковым временем.
Первый опрос после старта лога, авария уже активна Alarm Пишется с init->..., чтобы обозначить состояние на старте.
Первый опрос после старта лога, аварии нет ничего Это baseline; State по первому значению не пишется.
Следствие: переход 0025: 0x04 -> 0x01 сам по себе даёт только State. Если при этом ещё и снялась защита в 0027, появятся две строки: Alarm (снятие 0027) и State (смена режима).

Функция is_alarm

def _is_alarm(sig):
    status, warning, protection, error, temp_high, temp_low = sig
    return bool(warning or protection or error or temp_high or temp_low)

Важно: status в этой функции больше не участвует. Поэтому неизвестное значение 0025, например 0x05, не может попасть в Alarm; оно всегда State.

6. Один цикл опроса

Для каждого успешного опроса АКБ выполняется следующая логика:

  1. Построить sig из текущей телеметрии.
  2. Взять prev = alarm_sig.
  3. Определить два независимых изменения:
    • alarm_changed — изменилась любая часть (warning, protection, error, temp_high, temp_low);
    • state_changed — изменился status (0025).
  4. Если prev is None:
    • при активной аварии — одна строка Alarm с init->...;
    • иначе событийных строк нет.
  5. Если prev is not None:
    • alarm_changed → строка Alarm;
    • state_changed → строка State;
    • если оба — две строки, сначала Alarm, затем State.
  6. Независимо вычислить work_due: work_next_t is None or now >= work_next_t.
  7. Если событийных строк нет и Work не due — выйти, ничего не писать.
  8. Записать строки в порядке: Alarm, State, Work.
  9. Обновить alarm_sig = sig только после успешной записи событийных строк.
  10. work_next_t обновить только после успешной записи Work.

Схема решения

опрос АКБ→ sig = (S,W,P,E,T)→ сравнить с prev→ alarm_changed?→ State changed?→ Work due?→ запись строк

7. Формат CSV и колонка Changes

Колонка Changes добавляется в конец схемы, после Serial. Это сохраняет порядок старых колонок и совместимость со старыми логами: анализатор ищет колонки по имени и просто не найдёт новую в старых файлах.

... , "Status_Hex", "Warning_Hex", "Protection_Hex", "Error_Hex",
      "Balance_Hex", "Serial", "Changes"

Грамматика

Changes := change ("; " change)*
change  := source ": " old "->" new
source  := "S" | "W" | "P" | "E" | "T"
old,new := "0x" HEX4        для S/W/P/E
         | "normal" | "high" | "low"   для T
         | "init"            для первого сэмпла
  • Alarm-строка содержит только W, P, E, T. Порядок фиксированный: W, P, E, T.
  • State-строка содержит только S.
  • Work-строка — пустая ячейка Changes.
  • Hex — 4 цифры, верхний регистр: 0x0002, 0x1000.
  • Разделитель "; " (точка с запятой и пробел), без запятых внутри значения, чтобы CSV не квотировался без необходимости.
  • Перечисляются только изменившиеся поля. Неизменившиеся не пишутся.

Примеры значений

СитуацияLogChanges
Статус Standby → ChargingState S: 0x0000->0x0001
Появилось предупреждениеAlarm W: 0x0000->0x0002
Снялась защитаAlarm P: 0x1000->0x0000
Одновременно Warning и ProtectionAlarm W: 0x0000->0x0002; P: 0x0000->0x1000
ПерегревAlarm T: normal->high
Возврат температуры в нормуAlarm T: high->normal
Первый сэмпл с активным WarningAlarm W: init->0x0002
Плановая телеметрияWork пусто

8. Примеры

Во всех примерах время одинаковое для строк одного цикла; строки записаны в порядке Alarm → State → Work. Значения Status_Hex и других колонок в примерах сокращены до ..., чтобы показать только существенное.

8.1. Только смена режима

Было: S=0x0000, W=0, P=0, E=0, температура в норме.
Стало: S=0x0001.

2026-11-11 | 10:00:00,State,...,0x0001,0x0000,0x0000,0x0000,25.0,"S: 0x0000->0x0001"

Одна строка State. Alarm нет, потому что 0026/0027/0028/T не менялись.

8.2. Появилось предупреждение по 0026

Было: W=0x0000.
Стало: W=0x0002.

2026-11-11 | 10:00:01,Alarm,...,0x0001,0x0002,0x0000,0x0000,25.0,"W: 0x0000->0x0002"

8.3. Событие по 26, затем через секунду по 27, затем снова по 27

Это ваш сценарий. Каждый опрос — отдельная строка Alarm со своей дельтой.

ВремяЧто изменилосьLogChanges
10:00:000026: 0x0000 → 0x0002 AlarmW: 0x0000->0x0002
10:00:010027: 0x0000 → 0x1000 AlarmP: 0x0000->0x1000
10:00:020027: 0x1000 → 0x0000 AlarmP: 0x1000->0x0000
 
2026-11-11 | 10:00:00,Alarm,...,0x0001,0x0002,0x0000,0x0000,25.0,"W: 0x0000->0x0002"
2026-11-11 | 10:00:01,Alarm,...,0x0001,0x0002,0x1000,0x0000,25.0,"P: 0x0000->0x1000"
2026-11-11 | 10:00:02,Alarm,...,0x0001,0x0002,0x0000,0x0000,25.0,"P: 0x1000->0x0000"

В каждой строке только то, что изменилось в этом цикле. Предыдущие значения не повторяются.

8.4. Несколько регистров в одном цикле

Было: W=0, P=0.
Стало: W=0x0002, P=0x1000.

2026-11-11 | 10:00:00,Alarm,...,0x0001,0x0002,0x1000,0x0000,25.0,"W: 0x0000->0x0002; P: 0x0000->0x1000"

Одна строка Alarm за цикл, в Changes перечислены оба изменения.

8.5. Снятие аварии и смена режима одновременно

Было: S=0x0004 (Protect), W=0x0002, P=0x1000.
Стало: S=0x0001 (Charging), W=0, P=0.

2026-11-11 | 10:00:01,Alarm,...,0x0001,0x0000,0x0000,0x0000,25.0,"W: 0x0002->0x0000; P: 0x1000->0x0000"
2026-11-11 | 10:00:01,State,...,0x0001,0x0000,0x0000,0x0000,25.0,"S: 0x0004->0x0001"

Две независимые строки: Alarm фиксирует снятие 0026/0027, State — смену режима 0025. Обе имеют одинаковое время и одинаковый снимок телеметрии, но разные Log и Changes.

8.6. Вход в Protect без изменения 0027

Было: S=0x0001, P=0.
Стало: S=0x0004, P=0.

2026-11-11 | 10:00:01,State,...,0x0004,0x0000,0x0000,0x0000,25.0,"S: 0x0001->0x0004"

Только State. Alarm нет: аварийные регистры не менялись. Если защита реально сработала, изменится 0027 и появится отдельная строка Alarm.

8.7. Выход из Protect, но защита ещё активна

Было: S=0x0004, P=0x1000.
Стало: S=0x0001, P=0x1000.

2026-11-11 | 10:00:01,State,...,0x0001,0x0000,0x1000,0x0000,25.0,"S: 0x0004->0x0001"

Только State. Защита в 0027 не изменилась, поэтому нового Alarm нет; авария остаётся активной.

8.8. Нагрев и неизвестное значение 0025

2026-11-11 | 10:00:01,State,...,0x8000,0x0000,0x0000,0x0000,25.0,"S: 0x0000->0x8000"
2026-11-11 | 10:00:02,State,...,0x0005,0x0000,0x0000,0x0000,25.0,"S: 0x0000->0x0005"

Бит нагрева 0x8000 и неизвестное 0x0005 — это State. Функция _is_alarm() не смотрит на status, поэтому 0x05 не может стать Alarm.

8.9. Событие и Work в одном цикле

Work due, одновременно изменились 0025 и 0026.

2026-11-11 | 10:00:01,Alarm,...,0x0001,0x0002,0x0000,0x0000,25.0,"W: 0x0000->0x0002"
2026-11-11 | 10:00:01,State,...,0x0001,0x0002,0x0000,0x0000,25.0,"S: 0x0000->0x0001"
2026-11-11 | 10:00:01,Work,...,0x0001,0x0002,0x0000,0x0000,25.0,""

Три строки с одинаковым временем. Порядок строгий: Alarm, State, Work. work_next_t сдвигается только на запись Work; событийные строки его не трогают.

8.10. Старт лога при активной аварии

Первый опрос: W=0x0002, P=0, S=0x0001.

2026-11-11 | 10:00:00,Alarm,...,0x0001,0x0002,0x0000,0x0000,25.0,"W: init->0x0002"

Если в этот же момент due Work — после Alarm будет ещё строка Work. State по первому значению не пишется: это baseline.

8.11. Нет изменений

Подпись не изменилась, Work не due — файл не трогаем. Если Work due — пишем только Work с пустым Changes.

8.12. Пропущенные промежуточные состояния

Лог строится по опросам, а не по физическим событиям BMS. Если между двумя опросами регистр успел измениться и вернуться:

0027: 0x0000 -> 0x1000 -> 0x0000   (между опросами)

итоговая дельта равна нулю, и строка Alarm не появится. Если два разных регистра изменились между одним и тем же опросом, они попадут в одну строку Alarm с двумя дельтами. Это ограничение polling-лога; для гарантированного захвата каждого события нужен журнал событий самого BMS или более быстрый опрос.

9. Work: независимый период

  • work_due = cfg["work"] and (work_next_t is None or now >= work_next_t).
  • work_next_t = now + work_interval обновляется только после успешной записи строки Work.
  • Событие (Alarm или State) не меняет work_next_t и не отменяет плановую строку.
  • Если Work due и есть событие, пишутся обе (или три) строки в одном цикле.
  • Первый Work после старта пишется сразу: work_next_t is None.
Проверка: Work на 0, 5, 10, 15 с при событиях между ними должен дать последовательность Work, State, State, Work, Alarm, Work, Alarm, Work. Work-строки остаются на своих секундах.

11. Ошибки записи

Если запись в файл не удалась:

  • в last_err / log_err попадает текст ошибки;
  • alarm_sig возвращается к prev, чтобы событие не потерялось и было повторено на следующем цикле;
  • work_next_t возвращается к предыдущему значению, чтобы плановая строка Work не потерялась;
  • счётчики не увеличиваются.

12. Псевдокод

def log_row(parsed, addr):
    now = time.monotonic()
    with lock:
        st = get_log_state(addr)
        if not st["on"] or not st["path"]:
            return

        cfg  = dict(log_cfg)
        sig  = (status, warning, protection, error, temp_high, temp_low)
        prev = st["alarm_sig"]

        rows = []   # [(kind, changes), ...]

        if cfg["alarm"]:
            if prev is None:
                if is_alarm(sig):
                    rows.append(("Alarm", alarm_changes(None, sig)))
            else:
                alarm_changed = sig[1:] != prev[1:]
                state_changed = sig[0] != prev[0]
                if alarm_changed:
                    rows.append(("Alarm", alarm_changes(prev, sig)))
                if state_changed:
                    rows.append(("State", state_changes(prev, sig)))

        work_due = cfg["work"] and (
            st["work_next_t"] is None or now >= st["work_next_t"])
        if work_due:
            rows.append(("Work", ""))

        if not rows:
            return

        old_next = st["work_next_t"]
        if work_due:
            st["work_next_t"] = now + cfg["work_interval"]

        try:
            with write_lock:
                for kind, changes in rows:
                    write_row(parsed, addr, kind, changes)
            with lock:
                st["rows"] += len(rows)
                for kind, _ in rows:
                    if kind == "Alarm": st["alarm_rows"] += 1
                    if kind == "State": st["state_rows"] += 1
                    if kind == "Work":  st["work_rows"] += 1
                st["last_ts"] = now_iso()
                st["alarm_sig"] = sig
        except Exception as e:
            st["last_err"] = f"log {st['path']}: {e}"
            st["alarm_sig"] = prev
            st["work_next_t"] = old_next

Вспомогательные функции

def alarm_changes(prev, sig):
    # prev is None: первый сэмпл, перечисляем только активные регистры
    out = []
    for name, idx in (("W", 1), ("P", 2), ("E", 3)):
        new = sig[idx]
        if prev is None:
            if new:
                out.append(f"{name}: init->{hex4(new)}")
            continue
        old = prev[idx]
        if old != new:
            out.append(f"{name}: {hex4(old)}->{hex4(new)}")
    # температура
    if prev is None:
        if sig[4]: out.append("T: init->high")
        if sig[5]: out.append("T: init->low")
    else:
        if prev[4] != sig[4]:
            out.append("T: high->normal" if prev[4] else "T: normal->high")
        if prev[5] != sig[5]:
            out.append("T: low->normal" if prev[5] else "T: normal->low")
    return "; ".join(out)


def state_changes(prev, sig):
    return f"S: {hex4(prev[0])}->{hex4(sig[0])}"

13. Чек-лист selftest

  1. Status 0x00 -> 0x01 → State, Alarm нет.
  2. Status 0x01 -> 0x04 (вход в Protect) → только State.
  3. Status 0x04 -> 0x01 без изменений 26/27 → только State.
  4. Warning 0x0000 -> 0x0002 → Alarm.
  5. Warning 0x0002 -> 0x0000 → Alarm (recovery).
  6. Protection 0x0000 -> 0x1000 → Alarm.
  7. Protection 0x1000 -> 0x0000 → Alarm (recovery).
  8. Error 0x0000 -> 0x0010 → Alarm.
  9. Температура normal -> high и обратно → Alarm.
  10. Warning снялся + Status изменился → Alarm + State.
  11. Warning и Protection снялись + Status изменился → Alarm + State.
  12. Событие + Work due → Alarm/State + Work.
  13. Событие не меняет work_next_t.
  14. Нет изменений и Work не due → ничего не пишется.
  15. Первый сэмпл с активным Warning → Alarm с W: init->....
  16. Неизвестный Status 0x05 → State.
  17. Heating 0x8000 → State.
  18. Оба скрипта дают одинаковые Log и Changes.

14. Совместимость и миграция

  • Новая колонка Changes добавляется в конец, поэтому старые колонки не сдвигаются.
  • Старые CSV без Changes остаются читаемыми: анализатор ищет колонки по имени.
  • Значения Log: Alarm, State, Work. Старые файлы содержат только Alarm и Work; это нормально.
  • Версия в шапке скриптов: 3.5.
