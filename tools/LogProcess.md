## 1. Короткие ответы

| Вопрос | Ответ |
|---|---|
| Когда срабатывает аварийный профиль? | Когда меняется **сигнатура** состояния: `status` (r25), `warning` (r26), `protection` (r27), `error` (r28) или флаг выхода температуры за порог. |
| Пишется ли строка, если ничего не изменилось? | **Нет.** При стабильном состоянии файл не растёт. |
| Что происходит при снятии аварии? | Пишется **одна** строка с `Log=Alarm` — это запись восстановления. |
| Будут ли задвоения при снятии? | **Нет.** После записи восстановления новая сигнатура запоминается; повторные выборки с тем же состоянием ничего не пишут. Если в этом же цикле был должен писаться `Work`, он переносится — остаётся одна строка. |
| Температура: любое изменение? | **Нет, только пересечение порога.** Участвует только `Temp_Max` (регистр 0020): `>= 45 °C` или `<= 0 °C`. Изменение 22→44→23 °C аварийных строк не даёт. |
| Есть ли гистерезис по температуре? | **Нет.** Повторные переходы 44↔45 °C дают новую аварию каждый раз. |
| Могут ли профили мешать друг другу? | Нет: один файл, запись сериализована, за цикл максимум одна строка, приоритет у `Alarm`. |

## 3. Входные данные

`log_row(regs, addr)` вызывается после каждого успешного чтения блока регистров АКБ
(активный опрос, первичное сканирование, фоновый hot-plug, пассивный сниффер).
Внутри вызывается `decode_regs(regs)`, который даёт:

| Поле | Регистр | Что это |
|---|---|---|
| `status` | 0025 | состояние BMS (низкий байт: Standby/Charging/Discharging/Protect/Charging Lmt, бит `0x8000` — нагрев) |
| `warning` | 0026 | предупреждения (14 бит) |
| `protection` | 0027 | защиты (14 бит) |
| `error_code` | 0028 | ошибки измерения/ячеек |
| `temp_max` | 0020 | максимальная температура, °C (целое) |
| `temp_pcb`, `temp_avg`, `temp_sensors` | 0018, 0019, 0033–0035 | справочные температуры — **в критерии не участвуют** |

## 4. Сигнатура аварийного состояния

```python
def _alarm_signature(self, parsed):
    status     = parsed.get("status") or 0
    warning    = parsed.get("warning") or 0
    protection = parsed.get("protection") or 0
    error      = parsed.get("error_code") or 0
    t_max      = parsed.get("temp_max")
    temp_high  = t_max is not None and t_max >= ALARM_TEMP_HIGH_C  # 45.0
    temp_low   = t_max is not None and t_max <= ALARM_TEMP_LOW_C   # 0.0
    return (status, warning, protection, error, bool(temp_high), bool(temp_low))
```

Сигнатура — это кортеж из шести элементов. Именно его изменение является
триггером аварийного профиля.

### Что считается аварией

```python
def _is_alarm(sig):
    status, warning, protection, error, temp_high, temp_low = sig
    return bool(warning or protection or error or (status & 0x04)
                or temp_high or temp_low)
```

Авария активна, если выполнено **хотя бы одно**:

1. `warning != 0` — любой бит предупреждений;
2. `protection != 0` — любой бит защит;
3. `error != 0` — любая ошибка;
4. `status & 0x04` — состояние `Protect`;
5. `temp_max >= 45 °C`;
6. `temp_max <= 0 °C`.

Бит нагрева `0x8000` сам по себе аварией **не считается**, но входит в
сигнатуру через полное значение `status`.

## 5. Пошаговый алгоритм

Упрощённый псевдокод `log_row()`:

```python
parsed = decode_regs(regs)
now = monotonic()

# 1. Логирование вообще включено?
if not st["on"]:
    if log_auto:  # выбран хотя бы один профиль
        start_new_file(st, addr)
    else:
        return

cfg  = current_profiles()
sig  = alarm_signature(parsed)
prev = st["alarm_sig"]          # None после старта нового файла

kind = None

# 2. Профиль Alarm (проверяется первым)
if cfg.alarm and sig != prev:
    if is_alarm(sig) or (prev is not None and is_alarm(prev)):
        kind = "Alarm"
    st["alarm_sig"] = sig       # запоминаем даже если строку не пишем

# 3. Профиль Work
if kind is None and cfg.work:
    if st["work_next_t"] is None or now >= st["work_next_t"]:
        kind = "Work"

# 4. Ничего не пишем
if kind is None:
    return

# 5. Любая запись сбрасывает таймер Work
if cfg.work:
    st["work_next_t"] = now + cfg.work_interval

# 6. Запись под отдельным мьютексом
with _log_write_lock:
    if file_missing:
        write_header()
    write_row(kind)

# 7. Счётчики
st["rows"] += 1
st[f"{kind.lower()}_rows"] += 1
```

### Ключевые свойства шага 2

- Сигнатура обновляется **всегда**, когда профиль Alarm включён, даже если
  строка не пишется. Поэтому обычные переходы статуса не накапливаются и не
  выстреливают позже.
- Строка пишется, если **новое** состояние аварийное **или прежнее** было
  аварийным. Второе условие — это и есть запись восстановления.
- При первом сэмпле после старта файла `prev = None`:
  - авария уже есть → пишется стартовая строка `Alarm`;
  - аварии нет → строка не пишется, но нормальная сигнатура запоминается.

## 6. Температура: подробно

### Что участвует

Только `temp_max` — регистр `0020`, целое число °C.
`Temp_PCB`, `Temp_Avg` и `Temp_1…Temp_6` в критерий **не входят**
(они пишутся в CSV как телеметрия, но не вызывают аварийных записей).

### Критерий

```python
temp_high = temp_max >= 45      # ALARM_TEMP_HIGH_C
temp_low  = temp_max <= 0       # ALARM_TEMP_LOW_C
```

Пороги — константы в начале файла, меняются в одном месте.

### Примеры

| Последовательность `temp_max` | Аварийные строки |
|---|---|
| 22 → 23 → 24 → 30 → 44 | нет |
| 44 → 45 | одна `Alarm` (вход в перегрев) |
| 45 → 46 → 47 | нет (флаг `temp_high` уже `True`) |
| 47 → 44 | одна `Alarm` (выход из перегрева) |
| 44 → 45 → 44 → 45 | три `Alarm` (дребезг на пороге, гистерезиса нет) |
| 5 → 0 | одна `Alarm` (нижний порог) |
| 0 → -5 → 1 | `Alarm` при 0, затем `Alarm` при возврате |

Важно: «любое изменение температуры» **не** логируется. Внутри рабочего
диапазона (1…44 °C) изменения температуры аварийный профиль игнорирует.

Если включён профиль `Work`, сами значения температуры всё равно попадают в
периодические строки `Work` — но это плановая запись, а не событие.

### Пограничные случаи

- `temp_max == 0` трактуется как нижняя авария (`<= 0`).
- Если регистр 0020 недоступен, `decode_regs` подставляет `0`, что тоже даст
  `temp_low = True`. На исправной BMS блок из 39 регистров читается целиком,
  поэтому практически это не проявляется.
- Дребезг вокруг порога может дать несколько строк. Это следствие отсутствия
  гистерезиса; при необходимости можно добавить его в `_alarm_signature()`,
  например считать `temp_high` при `>= 45`, а снимать только при `<= 43`.

## 7. Жизненный цикл аварии

| Шаг | `prev_sig` | Новая `sig` | `_is_alarm(new)` | `_is_alarm(prev)` | Результат |
|---|---|---|---|---|---|
| Старт, всё нормально | `None` | норма | нет | — | строки нет, сигнатура запомнена |
| Старт, авария уже есть | `None` | авария | да | — | `Alarm` (baseline) |
| Появление аварии | норма | авария | да | нет | `Alarm` |
| Авария без изменений | авария | та же | да | да | профиль Alarm молчит (может писать `Work`) |
| Изменение битов аварии | авария A | авария B | да | да | `Alarm` |
| Смена статуса при активной аварии | авария A | авария B | да | да | `Alarm` |
| Полное снятие аварии | авария | норма | нет | да | `Alarm` (восстановление) |
| Норма без изменений | норма | норма | нет | нет | строки нет |
| Смена статуса без аварии | норма A | норма B | нет | нет | строки нет, сигнатура обновлена |

### Пример таймлайна (оба профиля, интервал 5 с)

```
t=0.0   старт                       → Work            (норма, baseline Alarm без строки)
t=5.0   планово                     → Work
t=7.2   warning 0x0000 → 0x0002     → Alarm           (авария, Work перенесён на 12.2)
t=12.2  планово                     → Work            (авария держится, сигнатура та же)
t=13.0  warning 0x0002 → 0x0003     → Alarm           (изменился набор битов)
t=18.0  планово                     → Work
t=20.0  warning 0x0003 → 0x0000     → Alarm           (восстановление, Work перенесён на 25.0)
t=25.0  планово                     → Work
```

Ни одна строка не повторяется: каждая отражает конкретное событие.

## 8. Поведение при снятии аварии

1. Приходит сэмпл с нормальными `r26/r27/r28`, без `Protect` и без выхода
   температуры за порог.
2. `sig != prev_sig`, при этом `_is_alarm(new) == False`, а
   `_is_alarm(prev) == True` → выбирается `kind = "Alarm"`.
3. Пишется **одна** строка восстановления. В ней:
   - `Log = Alarm`;
   - телеметрия и регистры **текущие, уже нормальные** (обычно `0x0000`);
   - отдельного признака «recovery» нет — восстановление определяется по
     нулевым аварийным регистрам и по соседним строкам.
4. Новая нормальная сигнатура сохраняется в `alarm_sig`.
5. Следующие сэмплы с тем же состоянием не пишут ничего.

### Будут ли задвоения

Нет, в штатном режиме:

- строка восстановления одна;
- повторная выборка с той же сигнатурой не пишет;
- если в этом цикле должен был писаться `Work`, он не пишется — `Alarm`
  имеет приоритет, а таймер `Work` переносится.

Возможные «похожие на дубли» ситуации — это не дубли, а разные события:

| Ситуация | Почему появляется несколько строк |
|---|---|
| Авария меняет биты (0x0002 → 0x0003 → 0x0002) | каждая смена сигнатуры — отдельное событие |
| Температура дребезжит на пороге 44↔45 | нет гистерезиса, каждый переход — событие |
| Статус меняется при активной аварии | `status` целиком входит в сигнатуру |
| Перезапуск логирования | создаётся **новый файл**, в нём снова пишется baseline-строка, если авария активна |

Теоретический крайний случай: если запись строки уже произошла, но затем
возникла ошибка файловой системы до обновления счётчиков, при следующем
сэмпле возможна повторная попытка. В обычной работе это не проявляется.

## 9. Профиль Work: как считает интервал

- Первая строка после старта файла пишется сразу (`work_next_t is None`),
  если в этом же сэмпле не сработал `Alarm`.
- Далее — не чаще, чем раз в `work_interval` секунд (по умолчанию 5.0,
  диапазон 1…3600, невалидное значение заменяется на 5.0).
- Таймер обновляется **любой** записью, в том числе аварийной. Поэтому авария
  сдвигает ближайшую плановую строку на полный интервал.
- Проверка интервала идёт по монотонным часам (`time.monotonic()`), перевод
  системного времени на неё не влияет.
- Если аварийная сигнатура меняется чаще, чем раз в интервал, плановые строки
  `Work` могут откладываться долго — это осознанный приоритет аварий. Как
  только состояние стабилизируется, `Work` возобновляется.

## 10. Одновременная работа профилей и отсутствие коллизий

- Оба профиля пишут в **один и тот же файл** АКБ
  (`bms_monitor_<ADDR>_<YYYYMMDD_HHMMSS>.csv`).
- За один вызов `log_row()` выбирается **не более одного** типа строки:
  сначала проверяется `Alarm`, затем `Work`.
- Если сработал `Alarm`, `Work` в этом цикле не пишется; его таймер сдвигается.
- Файловые операции защищены `_log_write_lock`, состояние — `self.lock`.
  `log_row()` вызывается только из потока опроса шины, HTTP-запросы записи в
  лог не инициируют, поэтому строки не перемешиваются и не интерливингуются.
- Заголовок файла создаётся ровно один раз — при первой фактической записи.

## 11. Когда файл создаётся, а когда нет

- Старт логирования (`Старт` или включение профиля) создаёт **путь** и
  состояние, но не файл на диске.
- Файл появляется при первой реальной записи.
- Профиль **только Alarm** при спокойном состоянии может работать сколько
  угодно — файла не будет вовсе (в таблице UI путь отображается, но на диске
  его нет). Это соответствует требованию «не писать, пока ничего не изменилось».
- Профиль **Work** создаёт файл на первом же сэмпле.
- Имя файла фиксируется при старте логирования и не меняется до следующего
  «Стоп/Старт».
- Структура колонок (число ячеек и датчиков) фиксируется по первой записи.

## 12. Формат строки

Колонка `Log` — вторая, сразу после `Date`:

```csv
Date,Log,addr,Voltage_V,...,Status_Hex,Warning_Hex,Protection_Hex,Error_Hex,Balance_Hex
2026-10-30 | 13:35:05,Work,0x01,52.31,15.0,...
2026-10-30 | 13:41:12,Alarm,0x01,52.10,0.0,...   ← авария
2026-10-30 | 13:44:30,Alarm,0x01,52.05,0.0,...   ← восстановление (регистры 0x0000)
```

Строка `Alarm` содержит полный снимок телеметрии на момент события, поэтому
по ней видно и значения ячеек, и температуру, и точные hex-коды регистров
`0025–0028`.

## 13. Изменение настроек на лету

| Действие | Поведение |
|---|---|
| Включить Alarm при работающем логе | на следующем сэмпле: если авария есть — baseline `Alarm`, иначе сигнатура запомнится молча |
| Выключить Alarm | сигнатура «замораживается»; события, произошедшие без профиля, не пишутся |
| Снова включить Alarm | возможна одна «догоняющая» строка: активация, изменение или восстановление относительно замороженной сигнатуры |
| Включить Work | первая плановая строка — на ближайшем сэмпле (если таймер не задан или уже истёк) |
| Выключить Work | `Alarm` продолжает работать, таймер Work не трогается |
| Изменить интервал | применяется к следующей записи; уже запланированное время не пересчитывается |
| «Стоп» | запись прекращается, автозапуск выключается, файл остаётся на диске |
| «Старт» | новый файл, `alarm_sig = None`, таймер Work сброшен |

## 14. Ограничения и на что обратить внимание

1. **Нет гистерезиса по температуре** — дребезг на 45 °C даёт серию строк.
2. **Участвует только `Temp_Max`** — перегрев отдельного датчика, не влияющий
   на максимум, не вызовет событие (но может попасть в `Warning`/`Protection`
   от BMS и тогда сработает по регистрам).
3. **Статус входит в сигнатуру целиком** — при активной аварии смена
   Charging/Discharging добавляет строку `Alarm`.
4. **Переходы статуса без аварии не логируются** — это осознанно, иначе
   «аварийный» лог заполнялся бы штатными режимами.
5. **Alarm-профиль не пишет периодический «heartbeat»** — при стабильном
   состоянии в файле может быть давно не было строк; это нормально.
6. **Приоритет аварий может откладывать Work** при частой смене аварийной
   сигнатуры.
7. **Восстановление не помечено отдельным словом** — только `Log=Alarm` и
   нулевые аварийные регистры.

## 15. Проверенные сценарии

Функциональные тесты подтвердили:

- Work: троттлинг по интервалу, все строки `Work`;
- Alarm: нет файла при спокойном состоянии; запись при появлении; отсутствие
  повторов при неизменном состоянии; одна запись при восстановлении;
- температура: событие только при переходе порога, без повторов внутри зоны;
- оба профиля: последовательность `Work, Alarm, Work`, без дублей;
- автозапуск лога для горячо подключённой АКБ;
- HTTP-интеграция: настройки применяются, строки с колонкой `Log` пишутся.

Результаты: `selftest OK`, `JS OK`, `ALL LOG PROFILE TESTS PASSED`,
`HTTP INTEGRATION OK`.
