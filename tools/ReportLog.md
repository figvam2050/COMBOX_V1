# Отчёт: двойное профильное логирование BMS (v2.4)

**Проект:** COMBOX & Vision BMS Monitor
**Изменённый файл:** `tools/bms_web.py`
**Дата:** 30.10.2026
**Объём файла после изменений:** 3 167 строк, ~152 КБ

---

## 1. Постановка задачи

Добавить в карту логирования (`📝 Запис CSV-лога`) два независимых профиля записи:

1. **Аварийные события** — регистры `0025–0028` (status / warning / protection / error) и температура.
   Если состояние не изменилось — в файл не писать.
2. **Анализ / тест ячеек** — периодическая запись с интервалом 5 с, интервал задаётся в окошке в карте лога.

Дополнительные требования:

- оба профиля могут работать одновременно и без коллизий;
- аварийные записи имеют приоритет;
- в CSV добавить колонку `Log` со значением `Alarm` или `Work`;
- в начале файла — краткое описание нового функционала;
- не добавлять ничего лишнего, максимально сохранить рабочую конфигурацию.

## 2. Краткий итог

Функционал реализован полностью:

| Требование | Реализация |
|---|---|
| Два чекбокса профилей в карте лога | `cfg_alarm`, `cfg_work` + пояснение и поле интервала |
| Профиль «только аварии» | `BmsBus._alarm_signature()`, `BmsBus._is_alarm()`, логика в `BmsBus.log_row()` |
| Запись только при изменении состояния | Сравнение сигнатуры `r25..r28` + температурных порогов с предыдущей |
| Профиль анализа с интервалом 5 с | `log_cfg["work_interval"]` (по умолчанию 5.0 с), настраивается из UI |
| Одновременная работа без коллизий | Один файл на АКБ + `_log_write_lock`, одна строка за цикл |
| Приоритет аварий | При совпадении цикла пишется `Alarm`, `Work` переносится на следующий интервал |
| Колонка `Log` | Вторая колонка CSV: `Date, Log, addr, ...`; значения `Alarm` / `Work` |
| Описание в начале файла | Блок `Dual logging profiles (v2.4)` в docstring |
| Сохранение рабочей конфигурации | Старые кнопки «Старт/Стоп», имена файлов, формат телеметрии и API сохранены |

## 3. Изменения в коде

### 3.1. Docstring (строки 21–31)

Добавлен блок описания:

```
  - Dual logging profiles (v2.4), selectable independently in the log card:
      * Alarm - logs only alarm events from registers 0025..0028
        (status / warning / protection / error) and temperature thresholds.
        Nothing is written while the register state is unchanged; a row is
        written on activation, on any change and on recovery.
      * Work  - periodic cell-analysis / test samples, interval set in the
        log card (default 5 s).
    Both profiles may run at once, sharing one CSV file per pack. Writes are
    serialized and Alarm rows always take priority over the periodic Work row
    (the Work sample is postponed, never duplicated). Column "Log" marks every
    row as Alarm or Work.
```

### 3.2. Константы (строки ~344–353)

```python
LOG_KIND_ALARM = "Alarm"
LOG_KIND_WORK = "Work"
DEFAULT_WORK_INTERVAL_S = 5.0
MIN_WORK_INTERVAL_S = 1.0
MAX_WORK_INTERVAL_S = 3600.0
ALARM_TEMP_HIGH_C = 45.0
ALARM_TEMP_LOW_C = 0.0
```

Пороги температуры вынесены в константы — при необходимости меняются в одном месте.

### 3.3. Формат CSV (строки 369–404)

В `build_log_header()` добавлена колонка `Log` **второй после `Date`**:

```csv
Date,Log,addr,Voltage_V,Current_A,Power_W,SOC_pct,Cap_Remaining_Ah,SOH_pct,
Max_Charge_A,Cycles,Full_Capacity_Ah,Designed_Cap_Ah,Cell_Num,
Cell_Min_V,Cell_Max_V,Cell_Diff_V,Temp_PCB_C,Temp_Avg_C,Temp_Max_C,
Cell_1_V,...,Cell_15_V,Temp_1_C,...,Temp_6_C,
Status_Hex,Warning_Hex,Protection_Hex,Error_Hex,Balance_Hex
```

В `build_log_values()` добавлен параметр `log_kind` (по умолчанию `Work`), который
пишется во вторую колонку.

Пример реальной строки из теста:

```csv
2026-10-30 | 14:35:49,Work,0x01,52.0,1.0,52.0,100,100,100,100,0,0.0,0.0,10,3.4,3.4,0.0,21,20,25,...,0x0000,0x0000,0x0000,0x0000,0x0000
```

Колонка `Log` находится после `Date`, поэтому офлайн-анализатор продолжает работать:
индекс даты теперь определяется через `header.indexOf('Date')`, остальные колонки
ищутся по имени.

### 3.4. Состояние логирования (строки 599–606, 655–710)

В `BmsBus` добавлены:

```python
self.log_cfg = {"alarm": True, "work": True, "work_interval": 5.0}
self.log_auto = False
self._log_write_lock = threading.Lock()
```

На пакет (`self.logs[addr]`) добавлены поля:

- `alarm_sig` — последняя сигнатура аварийного состояния;
- `work_next_t` — время следующей плановой записи (`time.monotonic()`);
- `alarm_rows`, `work_rows` — счётчики по типам;
- `rows`, `last_ts`, `path`, `on`, `cell_slots`, `temp_slots` — как раньше.

Новые/изменённые методы:

- `_start_log_state(st, addr)` — создание нового файла и сброс состояния;
- `set_log(on, addrs)` — как раньше, плюс управление `log_auto`;
- `set_log_cfg(alarm, work, work_interval)` — обновление профилей с валидацией
  интервала (1…3600 с).

### 3.5. Логика профилей (строки 932–1018)

**Сигнатура аварийного состояния:**

```python
(status, warning, protection, error, temp_high, temp_low)
```

где `temp_high = temp_max >= 45 °C`, `temp_low = temp_max <= 0 °C`.

**Событие аварии:** любой ненулевой `warning` / `protection` / `error`,
бит `Protect` (`0x04`) в `status` или выход температуры за порог.

**Когда пишется `Alarm`:**

- первая выборка, если авария уже активна;
- активация аварии;
- изменение набора аварийных битов;
- снятие аварии (запись восстановления);
- изменение температурного порога во время активной аварии.

Пока сигнатура не меняется — строка не пишется (требование «если состояние
регистров не изменилось, запись не делаем»). Обычные переходы статуса
(Standby → Charging → Discharging) без аварийных битов не логируются.

**Когда пишется `Work`:** если `now >= work_next_t`, затем `work_next_t`
сдвигается на `work_interval`.

**Приоритет и отсутствие коллизий:**

- проверка аварии выполняется первой;
- если в цикле пишется `Alarm`, то `work_next_t` сдвигается — плановая строка
  не дублируется, а переносится;
- запись в файл защищена `_log_write_lock`, поэтому строки не перемешиваются;
- оба профиля используют один и тот же файл АКБ, отдельные файлы не создаются.

### 3.6. Снимок состояния и API (строки 1188–1234, 3307–3316)

В `/api/data` добавлено:

- `log_cfg` — текущие настройки профилей;
- в `log_files` — `alarm_rows`, `work_rows`;
- в данных пака — `log_alarm_rows`, `log_work_rows`.

Новый endpoint `POST /api/logcfg`:

```json
{"alarm": true, "work": true, "work_interval": 5}
```

Ответ:

```json
{"ok": true, "log_cfg": {"alarm": true, "work": true, "work_interval": 5.0}}
```

Существующие `/api/log`, `/api/mode`, `/api/rescan` не изменены.

### 3.7. Интерфейс (строки 1269–1275, 1695–1714, 3187–3265)

В карте «Запис CSV-лога» добавлен блок **«Профілі запису»**:

- чекбокс **🚨 Лише аварійні події** (с пояснением регистров и порога температуры);
- чекбокс **🔬 Аналіз / тест комірок** + числовое поле интервала (`1…3600`, шаг 1, по умолчанию 5);
- пояснение: колонка `Log`, приоритет `Alarm`, общий файл без коллизий.

Дополнительно:

- в таблице файлов показываются счётчики `A n / W n`;
- в карточке АКБ — строка `Alarm / Work`;
- состояние чекбоксов и интервала синхронизируется с сервером при каждом опросе;
- `saveLogCfg()` отправляет настройки на `/api/logcfg`.

### 3.8. Автозапуск

Если выбран хотя бы один профиль, то при появлении новой АКБ (в том числе
горячим подключением) для неё автоматически создаётся лог. Кнопки
«Старт/Стоп записи» работают как раньше: «Стоп» отключает автозапуск,
«Старт» включает его снова.

## 4. Поведение профилей

| Ситуация | Alarm | Work | Что попадёт в файл |
|---|---|---|---|
| Оба профиля включены, аварий нет | нет события | каждые 5 с | строки `Work` |
| Оба включены, появилась авария | смена сигнатуры | плановая запись переносится | одна строка `Alarm` |
| Авария держится, регистры не меняются | сигнатура та же | каждые 5 с | только `Work` |
| Авария снята | смена сигнатуры | по расписанию | строка `Alarm` (восстановление) |
| Только Alarm, состояние стабильно | нет записи | — | файл не растёт |
| Только Alarm, температура вышла за порог | событие | — | строка `Alarm` |
| Только Work | — | по интервалу | строки `Work` |

## 5. Совместимость

- Имена файлов прежние: `bms_monitor_<ADDR>_<YYYYMMDD_HHMMSS>.csv`.
- Кнопки «Старт записи (усі АКБ)» и пер-паковый старт/стоп сохранены.
- Формат телеметрии не менялся — только добавлена колонка `Log`.
- Офлайн-анализатор понимает и новый, и legacy-формат.
- Профили по умолчанию включены оба, поэтому после нажатия «Старт» запись
  ведётся без дополнительных действий.
- Единственное осознанное изменение частоты: профиль `Work` пишет раз в 5 с,
  а не на каждый опрос шины (~0.35 с), как было раньше. Это и есть требуемый
  режим анализа; интервал настраивается.

## 7. Как пользоваться

1. Запустить: `python tools/bms_web.py` (или `--mock` для проверки без BMS).
2. Открыть `http://127.0.0.1:8080`.
3. В карте «Запис CSV-лога» выбрать профили:
   - только аварии — оставить включённым первый чекбокс;
   - анализ ячеек — второй чекбокс и нужный интервал.
4. Нажать «Старт записи (усі АКБ)».
5. В CSV смотреть колонку `Log`: `Alarm` или `Work`.
